# Spec E —— 单 tape 真相源裂缝修复（discovery / handle.status）

> **状态**：spec（契约 + 方向级方案），待排期实现
> **范围**：`orca/iface/web/run_manager.py` 的 `discover_runs` legacy 分支 + in-memory 分支 status 派生口径
> **不动**：events/、replay.py、tape.py 任何契约；不引入第二真相源
> **依据**：[phase-3-events.md](phase-3-events.md) §1 / §3.4 / §6.0 铁律 1、4 · [TASK.md](../TASK.md) §3

## 1. 背景与根因

### 1.1 为什么「单 tape 真相源」是底线

phase-3-events.md §1 把 AgentHarness 的灾难归因为「多真相源 + 双路径」：5 个 sidecar 投影 + 4 种 replay 策略 + 双 store，必然漂移。Orca 的回应是 12 条设计规则之首两条：

> 1. **Tape 是唯一真相源**。无并行内存 list（避免 Conductor `_event_history`）。
> 2. **一条读路径**。streaming = replay = read tape。

落到 discovery / list 路径上的等价约束（phase-3 SPEC §6.0 铁律 1、`orca/events/__init__.py:9`、`orca/events/tape.py:1-19`）：**对外暴露的 `RunSummary.status / progress / cost / elapsed / event_count` 必须从 tape fold 派生**，而不是从一个并行写的字段、一个 hardcoded 字面量、或一个内存标记读出。`replay_state(tape)` 是唯一派生函数（`orca/events/replay.py:33-41`，纯 reducer fold，重放两次结果相同）。

discovery 是用户重连后看到 run 列表的入口（`tars run --background` 跑完后用户回来看）。这一路一旦不读 tape，就是真相源裂缝——用户看到的 status 与 tape 实际记录分歧。

### 1.2 这两处怎么破的

| # | 位置 | 现象 | 为何是裂缝 |
|---|---|---|---|
| E-1 | `discover_runs` legacy 分支（run_manager.py:1420-1435）| 对每个旧 BgRunMeta **硬编码** `status="cancelled"` / `progress="?"` / `cost=0.0` / `event_count=0` | tape_path 已读到（1413）却从不 replay； tapes 里 `workflow_completed` / `workflow_failed` / crash 截断的真实终态被无视。legacy run 实际 completed → 列表显示 cancelled |
| E-2 | in-memory discovery 分支（run_manager.py:1380-1401，含 `event_count=0` 字面量 @1398）+ `_meta_from_handle`（1250）+ `_run_with_sem`（1871-1888）| `RunSummary.status` 取 `handle.status`（runtime 内存标记），**不**从 tape 派生；`event_count=0`（1398）同样是字面量硬编码 | emit(workflow_completed) 落 tape 与 `handle.status = "completed"`（1884）之间存在窗口；窗口内 `list_runs` 返 running 而 tape 已 completed。同一 run 在「live」与「重连后（attached 走 `_summary_from_tape`）」可能呈现不同 status。注：in-memory 分支的 `status` / `event_count` 字面量按 C1 豁免为 perf 占位符，**必须** docstring 标注（AC7），`progress/cost/elapsed` 仍走 replay_state |

E-1 是直接违反铁律 1（hardcoded 字面量取代 tape 派生）。E-2 是设计上有意保留的「实时快速通道」（run_manager.py:967-968 注释自承），但代价是与 tape 真相非原子——需要把契约边界显式化，而不是消灭它。

## 2. 现状证据（file:line，已实读核实）

### E-1：legacy 分支硬编码 cancelled

```
orca/iface/web/run_manager.py:1408-1435
```

- **1409** `_list_legacy_metas()` 返回旧 BgRunMeta 列表（`SimpleNamespace(run_id, yaml_path, started_at, tape_path)`，定义在 2144-2171）。
- **1413** `tape_path = Path(getattr(lm, "tape_path", "") or "")` —— tape 路径**已读到**。
- **1414-1419** 仅 `stat()` 校验文件存在；**从不 replay**。
- **1420-1435** 直接 `RunSummary(status="cancelled", progress="?", cost=0.0, elapsed=0.0, event_count=0, source="legacy")`。**所有字段字面量**，无一从 tape fold。

对比 attached 分支（1360-1377）走 `_summary_from_tape(tape_path, project_id=..., project_name=..., source="attached")`（1593-1657）：status/progress/cost/elapsed/event_count **全部**从 `_scan_meta_overview_cached(tape_path)` + `_scan_tape_timebounds(tape_path)` 派生。同一份 tape，attached 派生、legacy 硬编码——双口径。

**用户可观察后果**：
- legacy run tape 末行 `workflow_completed` → 列表显示 `cancelled`，用户误以为被取消而重跑，浪费 token / 重复副作用（写文件、调外部 API、扣额度）。
- legacy run 实际 crash（tape 截断在 `node_started`，无终态事件）→ 列表显示 `cancelled`，**掩盖 crash 信号**，与铁律 4「fail loud」直接冲突。
- 即便 legacy run 真被 cancel，status 也应从 tape 是否有 `workflow_cancelled` 派生，而非默认值。

### E-2：in-memory status 取 handle.status 而非 tape

```
orca/iface/web/run_manager.py:1380-1401  # in-memory discovery
orca/iface/web/run_manager.py:1210-1255  # _meta_from_handle
orca/iface/web/run_manager.py:1871-1888  # _run_with_sem（status 赋值点）
orca/iface/web/run_manager.py:964-973    # list_runs（同口径）
```

- **1380-1401** in-memory discovery：`status=meta.status`，meta 来自 `_meta_from_handle`。
- **1250** `_meta_from_handle` return `RunMeta(status=handle.status, ...)` —— **唯一不从 tape 派生的字段**（同函数内 progress/cost/workflow_name 全部走 `replay_state(handle.tape)`，1230）。
- **1882-1888** `await orch.run()` 内部 emit `workflow_completed`（写 tape）→ 返回 → 才执行 `handle.status = "completed"`。两步之间存在 asyncio 调度窗口。
- **967-968** `list_runs` docstring 自承设计意图：「元数据从 `replay_state(handle.tape)` 派生（progress/cost）……status 取 `handle.status`（**实时**）」。即设计上把 status 当快速 hint，**代价是与 tape 真相非原子**。

非原子窗口的可观察后果：emit 完成 → status 赋值之间，前端轮询 `list_runs` 收到 `running`，但同 run 在用户重连（attached 分支走 `_summary_from_tape`）后变成 `completed`。同一 run 在「live」与「重连后」status 不一致——这是双源（handle.status vs tape）的必然代价，不是 bug 而是未显式化的契约边界。

## 3. 不变式 / 契约

| # | 契约 | 出处 |
|---|---|---|
| C1 | **legacy/attached 分支**的 `RunSummary.status / progress / cost / elapsed / event_count` 必须从 tape fold 派生，禁字面量、禁并行字段。**in-memory 分支允许 `status` 取 `handle.status`、`event_count` 取字面量 0**（perf 占位符；注：handle 不持有 `event_count` 属性，run_manager.py:1398 当前即字面量 0），但 **`progress` / `cost` / `elapsed` 仍走 `replay_state(handle.tape)`**。该豁免必须在 `_meta_from_handle` / `list_runs` / `discover_runs` docstring 显式标注（AC7） | 铁律 1（phase-3 §6.0）+ `events/__init__.py:9`；in-memory 豁免为 perf 权衡，**禁止扩张到 E-2 让 in-memory 也走 `_scan_meta_overview_cached`** |
| C2 | **派生口径在 legacy / attached 两个 tape-derived 分支下一致**：同一个 `_summary_from_tape`（或等价的 `replay_state` fold）。in-memory 分支不参与该统一（见 C1 豁免） | DRY（CLAUDE.md 代码质量底线 6）+ 一条读路径（铁律 2） |
| C3 | **`handle.status` 是实时 hint，非权威；权威 status 永远在 tape**。in-memory 分支允许用 hint 作快速通道，但**必须**：(i) docstring 显式标注边界；(ii) 在「终态稳态」下与 tape-derived status 等价（AC8）；(iii) 在**公共方法 docstring + 字段行注释**注明 hint 语义（OpenAPI description 透传前端属前端 phase，非本 spec 范围） | 铁律 1 的弱化应用（hint ≠ 真相），承认 in-memory 与 attached 在终态窗口内 transient 不一致是设计 trade-off |
| C4 | **tape 损坏 / 缺失 → fail loud（warn + skip 或降级显式标注）**，禁静默 fallback 到「cancelled」字面量 | 铁律 4（phase-3 §6.0） |
| C5 | **不引入第二真相源**：不新增 sidecar、不新增内存状态字段、不缓存 status；cache 仅作 perf 优化且删了能从 tape 完全重建（与 `_scan_meta_overview_cached` 1380 已有契约一致） | 铁律 1 + run_manager.py:1479-1481 |

## 4. 方案（方向级，不写完整代码）

### 4.1 修复 E-1：legacy 分支走 `_summary_from_tape`

**核心**：把 1420-1435 的字面量构造，替换为与 attached 同款的 `_summary_from_tape` 调用。统一口径，消除双源。

**前置改动（N1，fail loud 修复）**：`_summary_from_tape`（run_manager.py:1610-1613）当前 `except: 静默 return None`——corrupt tape 时既不抛也不 warn。本 spec 要求**内层 except 补 `logger.warning(..., exc_info=True)` 再返 None**。理由：(1) AC5「日志 warning」否则不可达（外层 §4.1 的 `except` 永不触发，因内层吞了）；(2) bonus 修复 attached 分支（1366-1370）当前的静默问题；(3) 符合铁律 4 fail loud。外层 §4.1 的 `except` warn 可保留（双 warn 可接受，语义不同：内层「tape 损坏」/外层「discovery skip」），也可移除外层冗余 warn 由实现期定。

```
# 伪代码（方向，非最终实现）
#
# E2：三分支均显式 seen_ids.add，AC9 不留绕过空间。
# E10：三分支机制**故意非对称**（与代码循环顺序 attached → in-memory → legacy 一致）：
#   - attached 分支：源是注册表扫的 tape 文件，可能命中 live run 的 tape →
#     现有机制 `if summary.run_id in self._runs: continue`（skip-if-in-self._runs）。
#   - in-memory 分支：源是 self._runs（live 权威）→ 无条件 overwrite 入 summaries，
#     并无条件写入 new_index（in-memory 是最高优先级真相，attached 同 run_id 已被前一步 skip）。
#   - legacy 分支：源最弱（旧 BgRunMeta，可能 stale）→ skip-if-in-seen_ids +
#     skip-if-in-new_index（双防御），仅在更优先分支未占时入列表。
#   机制非对称的理由：in-memory 是 live 权威故 overwrite；attached 中间故 skip-if-live；
#   legacy 最弱故 skip-if-任何更优先源已占。**禁止实现期「统一」为同机制以免破坏优先级**。
seen_ids: set[str] = set()  # 跨三分支共享 dedup

# --- attached 分支（伪代码示意，已存在 1360-1377）---
for tape_path in sorted(runs_dir.glob("*.jsonl")):
    summary = self._summary_from_tape(..., source="attached")
    if summary is None:
        continue
    if summary.run_id in self._runs:  # 现有：live 已注册 → skip（attached < in-memory）
        continue
    if summary.run_id in seen_ids:    # E2：显式 dedup（同 tape 在多项目下重复 glob 命中）
        continue
    seen_ids.add(summary.run_id)      # E2：attached 也 add
    summaries.append(summary)
    new_index[summary.run_id] = (pid, tape_path, name)

# --- in-memory 分支（伪代码示意，已存在 1380-1401）---
for handle in self._runs.values():
    meta = self._meta_from_handle(handle)
    summary = RunSummary(..., status=meta.status, event_count=0, ...)  # C1 豁免
    if summary.run_id in seen_ids:    # E2：显式 dedup（理论上 attached 不会先占，因 attached
        continue                      #      skip-if-in-self._runs；此处防御重复 handle）
    seen_ids.add(summary.run_id)      # E2：in-memory 也 add
    summaries.append(summary)         # in-memory 无条件 overwrite 入列表（最高优先级）
    new_index[summary.run_id] = (...)  # 无条件 overwrite

# --- legacy 分支（本 spec 新增）---
for lm in legacy_metas:
    tape_path = Path(getattr(lm, "tape_path", "") or "")
    # 开放项4：tape_path 相对路径 → 视为缺失（resolve 失败走 AC4 warn+skip）
    if not tape_path.is_absolute() or not tape_path.is_file():
        logger.warning("legacy run %s tape 缺失或相对路径：%s", lm.run_id, tape_path)
        continue
    try:
        summary = self._summary_from_tape(
            tape_path, project_id=None, project_name="Legacy", source="legacy",
        )
    except Exception:
        # 注：内层 _summary_from_tape 已 warn（N1），此处保留外层 warn 表「discovery skip」
        logger.warning("legacy run %s tape 解析失败 skip", lm.run_id, exc_info=True)
        continue
    if summary is None:
        continue  # 0 有效事件 / 空 tape → None
    # E5：run_id 不一致 warn（AC10 锚点）——lm.run_id 可能来自 data.run_id 或 meta_file.stem
    # 三源（见 _list_legacy_metas 2165），统一在此一处覆盖
    if summary.run_id != lm.run_id:
        logger.warning(
            "legacy meta run_id mismatch: meta=%s tape_stem=%s (using tape)",
            lm.run_id, summary.run_id,
        )
    if summary.run_id in seen_ids:  # E2：legacy dedup（撞 attached/in-memory → skip）
        continue
    seen_ids.add(summary.run_id)    # E2：legacy 也 add
    summaries.append(summary)
    if summary.run_id not in new_index:  # N5：legacy 仅在未占时写入（最低优先级）
        new_index[summary.run_id] = (None, tape_path, "Legacy")
```

> 实现期可选：把「dedup check + add + append + new_index 写入」抽成 helper（如 `_emit_summary(summary, new_index, seen_ids, *, source_priority)`），三分支统一调用。spec 不强约束 helper 与否，但 **AC9 要求三分支均能验证去重**（不允许某分支靠注释/隐式 skip 绕过）。

**关键点**：
- **DRY**：复用 `_summary_from_tape`，不为 legacy 造第二条派生路径。
- **dedup（P1 / E2）**：`seen_ids` 跨 attached / in-memory / legacy 三分支**均显式 add**，无分支靠注释或隐式 skip 兜底（AC9 三对碰撞全覆盖）。
- **三分支机制非对称（E10）**：见伪代码顶部声明。机制差异是设计——in-memory live 权威故 overwrite；attached 中间故 skip-if-in-self._runs；legacy 最弱故 skip-if-seen + skip-if-in-new_index 双防御。**禁止实现期统一为同机制**。
- **new_index 写入优先级（N5）**：in-memory 无条件 overwrite；attached 仅 skip live；legacy 仅在未占时写入。整体优先级 in-memory > attached > legacy。
- **workflow_name 退化（E11，DRY 胜）**：选定**接受 `tape_path.stem` 退化**——不在 `_summary_from_tape` 之外传 `yaml_path.stem` hint（那会引入第二条 workflow_name 派生路径，违 AC6 DRY）。`_summary_from_tape` 内部走 `_topology_workflow_name_from_tape(tape_path) or tape_path.stem`（1619）已足够；tape 里有 `workflow_started.data.workflow_name` 命中即用，miss 时退化到 stem。
- **project_id / project_name**：legacy 无项目归属，保持 `None / "Legacy"`（与原 1425-1426 一致）。
- **run_id**：`_summary_from_tape` 用 `tape_path.stem`（1646）。若与 `lm.run_id` 不一致以 tape_path.stem 为准（tape 是真相），并记 warning（E5 / AC10）。

### 4.2 修复 E-2：显式标注 handle.status 为 hint，收窄双源窗口

E-2 是设计上的 trade-off（实时性 vs 原子性），不能简单消灭。两个方向，实现期选一（spec 不强约束，但必须显式化）：

**方向 A（推荐，轻量）：契约文档化 + 不动代码**
- 在 `_meta_from_handle`（1210-1255）和 `list_runs`（964-973）docstring 强化声明：`handle.status` 是「实时 hint，权威看 tape；discovery 列表的 in-memory 分支与 attached 分支在终态窗口内可能 transient 不一致」。
- 在 `RunMeta` / `RunSummary` 类型注释或字段注释标注 `status` 字段的 hint 语义。
- 不改运行时行为。trade-off：保留实时性，承认非原子窗口，靠文档防误解。

**方向 B（可选，重）：收窄窗口**
- 在 `_run_with_sem`（1882-1888）中，让 `orch.run()` 内部 emit 终态事件后、返回前，同步把 `handle.status` 设为终态（或让 Orchestrator 通过回调在 emit 完成的同一同步点设置）。缩短但无法消灭窗口（emit→tape.flush 与 status 赋值仍非原子）。
- 代价：增加 Orchestrator 与 RunManager 的耦合（Orchestrator 反向知道 handle），违反依赖单向（events → schema，exec/run 单向依赖）。**不推荐**，除非实现期证明窗口实际造成用户可观察 bug。

**方向 C（可选，订阅式）**：RunManager 在 `_run_with_sem` 启动时让 handle 通过 `handle.bus.subscribe()` 注册一个 listener，收到 `workflow_completed/failed/cancelled` 终态事件后同步设置 `handle.status`。
- 合法性：iface → events 订阅方向合法（不违反单向依赖）。
- **不推荐**：(i) 每 run 增 1 Subscription + 1 listener task，资源与 lifecycle 复杂度上升（teardown 需 unsubscribe + 异常处理）；(ii) 与 Orchestrator 已 emit 终态的职责重叠——Orchestrator 是权威 emitter，RunManager 二次监听同一事件流是反模式（重复消费）；(iii) 窗口仍非零（emit → listener 调度 → status 赋值，仍跨 asyncio 点）；(iv) 复杂度收益比方向 A 差（A 零代码 + 文档化即解决问题）。

**spec 推荐**：方向 A。理由：(1) E-2 的实际可观察影响远小于 E-1（窗口是毫秒级 asyncio 调度，用户轮询周期通常秒级）；(2) 方向 B 损失依赖单向性不划算；(3) 方向 C 资源/lifecycle 复杂度 + 重复消费反模式不划算；(4) 把 hint 语义文档化即可防「以为 status 是权威」的误解。

### 4.3 不做的事（与 §5 范围边界呼应）

- ❌ 不改 `_summary_from_tape` 的派生逻辑（它已是正确口径）；**例外（N1）**：仅补内层 except 的 `logger.warning`（fail loud 修复，不改派生语义）。
- ❌ 不改 events/、replay.py、tape.py。
- ❌ 不新增 sidecar、不新增内存状态字段、不缓存 status。
- ❌ 不消灭 `handle.status`（它是 cancel 路径 / list_runs 实时性的必要 hint，run_manager.py:1101、1131）。
- ❌ 不为 legacy run 造第二条派生路径（DRY）。

## 6. 验收标准（可验证）

### AC1 — legacy run 实际 completed 时 discovery 显示 completed（核心）

- **前置**：构造一个 legacy BgRunMeta（`~/.orca/runs/<run_id>.json`，含 `tape_path` 指向一个真实 tape），其 tape 末行是 `workflow_completed`。
- **动作**：调用 `RunManager.discover_runs()`。
- **断言**：返回的 RunSummary 中，该 run 的 `status == "completed"`（**非** `"cancelled"`），`source == "legacy"`，`event_count > 0`，`cost` 来自 tape（非硬编码 0.0）；`progress` 匹配正则 `^\d+/\d+$`（**禁词「形如」已删**——必须严格匹配该正则），且 `done`/`total` 与 `_summary_from_tape` 对该 tape 的返回值**逐字相等**。
- **N8 补强**：patch `_summary_from_tape` 让其返回带 `cost=1.23` 的固定 summary，断言 discover_runs 返回值 round-trip == 1.23（防止被覆盖为 0.0）。

### AC2 — legacy run 实际 crashed（tape 无终态事件）不被误标 cancelled（E9 trade-off）

- **前置**：legacy tape 截断在 `node_started`，无 `workflow_completed/failed/cancelled`。
- **断言**：**该 run 出现在列表**（不被 skip），且 `status == _summary_from_tape(tape_path, ...)` 对该 tape 的确定返回值（按 1620-1632 的 `overview.run_status` 映射，预期为 `live-pending` 或 `running`），**不**是 `cancelled`；不抛异常。
- **E9 trade-off（接受）**：crashed legacy 显示 `live-pending`/`running` 可能比原 `cancelled` 更误导（用户 attach 死进程）。**接受**——tape 真相 > 用户感知便利（铁律 1 优先），见 §10 第三破坏性变更。

### AC3 — legacy run 真被 cancel 时显示 cancelled

- **前置**：legacy tape 含 `workflow_cancelled` 事件。
- **断言**：`status == "cancelled"`（从 tape 派生，与 AC1/AC2 同口径）。

### AC4 — legacy tape 缺失 / 相对路径 fail loud（E13 双 fixture）

- **前置 (a)**：BgRunMeta 的 `tape_path` 指向不存在的绝对路径；同时构造另一个正常的 legacy run（其 tape 存在且 completed）。
- **前置 (b)**（E13 / 开放项 4）：BgRunMeta 的 `tape_path` 是相对路径字符串（如 `"./tape.jsonl"`），**即使 cwd 下存在同名文件**也视为不可定位。
- **断言**：(a) 与 (b) 两种 fixture 下，discovery 均不崩列表，**列表长度 == 期望正常 run 数**（问题 run 不计入）；该 run 被 skip；日志有 warning（不静默）。

### AC5 — legacy tape 损坏 fail loud（E3 重写，去内/外层区分）

- **前置**：tape 文件存在但内容是乱码 / 0 有效事件。
- **断言**：该 run 被 skip；caplog 至少 1 条 warning **归因于该 corrupt tape**（消息内容含 `run_id` + tape path 字符串，便于稳定 grep）；不崩列表。不区分 warning 来自内层还是外层 except——只要存在「含 run_id + tape path」的 warning 即可。

### AC6 — 派生口径 DRY（attached 与 legacy 同路径）

- **断言**：grep `discover_runs` body，legacy 分支与 attached 分支调用同一个 `_summary_from_tape`；无第二条 status 派生逻辑；无 `status="cancelled"` 字面量（除 `_summary_from_tape` 内部 1627 的 `wf_status=="cancelled"` 映射）。
- **E11 补强**：`workflow_name` 在 `_summary_from_tape` 之外的后处理**仅允许在 tape 无 `workflow_started.data.workflow_name` 时**（即接受 `tape_path.stem` 退化，禁止传 `yaml_path.stem` hint 等第二条派生路径）。

### AC7 — handle.status hint 语义文档化（E-2 方向 A，E12 修订）

- **断言（机械可验）**：
  - (a) `_meta_from_handle`、`list_runs`、**`discover_runs`** 三个**公共方法 docstring** 必命中关键词集 {`hint`, `tape`, `权威`, (`transient` 或 `非原子`)}（中文/英文均可，关键词作为概念存在，由实现选用准确表达）。
  - (b) `RunMeta.status` / `RunSummary.status` 类型定义处加字段行注释 `# hint: 权威在 tape`（或等价英文）。注：OpenAPI description 把 hint 透传给前端属前端 phase 职责，非本 spec 范围。
  - (c) docstring 显式说明 in-memory 分支的 `status`/`event_count` 取 handle 字段（注：`event_count` 是字面量 0，handle 不持有该属性）属 C1 perf 豁免，`progress/cost/elapsed` 仍走 replay_state。

### AC8 — in-memory 与 attached 在稳态下 status 一致（不回归）

- **前置**：run 完成后（handle.status 已赋值 completed）。
- **动作**：分两次 `discover_runs()` 调用对比——(i) in-memory：run handle 仍在 `self._runs`；(ii) 模拟 restart：清空 `self._runs`，仅靠 attached 分支（tape 文件 + 注册表）发现该 run。
- **断言**：两次调用对该 run 返回相同 `status`（`completed`）。

### AC8b — `_meta_from_handle` replay 失败降级路径（E7 重写为非回归守卫）

- **性质**：**非回归守卫**——当前代码（run_manager.py:1241-1250）已 `status = handle.status` 且有 warn，零改动即应通过；本 AC 的目的是禁止后续回归（如有人改成抛异常、或静默吞错、或 status 不再取 handle.status）。
- **前置**：构造 `_meta_from_handle` 内 `replay_state(handle.tape)` 抛异常的场景（如 tape 损坏但 handle 仍 live），触发 1241-1250 降级分支。
- **断言**：返回的 RunMeta `status == handle.status`（不抛、不静默）；caplog 有 warning 且**消息含 `run_id` + 标记字符串 `replay-degraded`**（强制稳定 grep 锚点，便于 CI / 跨版本检测）。

### AC9 — 三分支 dedup 全覆盖（E2 重写）

- **前置**：枚举三对 run_id 撞车场景：
  - (i) **attached × attached**：两个注册项目的 `runs/` 都 glob 到同一个 tape_path（如 symlink / 共享目录）。
  - (ii) **attached × legacy**：一个 attached tape 与一个 legacy BgRunMeta 共用 run_id。
  - (iii) **in-memory × legacy**：一个 in-process run（`self._runs`）与一个 legacy BgRunMeta 共用 run_id。
- **断言（每对）**：`discover_runs()` 返回的 summaries 列表中该 run_id **仅出现一次**；`_run_path_index` 中该 run_id 只有一条记录；**声明 source 优先级胜出规则**：(i) attached × attached → 任意一个胜出均可（同 tape 派生，等价），但必须只一个；(ii) attached > legacy（attached 胜）；(iii) in-memory > legacy（in-memory 胜）。
- **机制要求**：attached / in-memory / legacy **三分支均显式 `seen_ids.add(summary.run_id)`**（不允许某分支靠注释或 `skip-if-in-self._runs` 隐式兜底——后者只能 dedup in-memory 维度，对 legacy 维度无效）。

### AC10 — BgRunMeta.run_id 与 tape_path.stem 不一致（E6 重写，覆盖三源）

- **背景**：`_list_legacy_metas`（run_manager.py:2165）的 run_id 有三个来源：`data.get("run_id")` / `meta_file.stem` fallback / `tape_path.stem`（`_summary_from_tape` 用此）。
- **前置**：构造 BgRunMeta 使 `lm.run_id` 来自任一来源（如 `data.run_id="abc"` 或 `meta_file.stem="abc"`），但其 `tape_path` 的 stem = "xyz"。
- **断言**：**无论 `lm.run_id` 来自三源中的哪一个**，只要 `lm.run_id != tape_path.stem` 即：`discover_runs()` 返回的 RunSummary `run_id == "xyz"`（以 tape_path.stem 为准，tape 是真相）+ caplog 有 warning（消息含 meta run_id 与 tape_stem）。一处 AC 覆盖三源（§4.1 伪代码中 `if summary.run_id != lm.run_id: warn` 是统一锚点）。

### AC11 — 不引入第二真相源（E8 重写为语义版）

- **断言（静态 grep + 语义判断）**：
  - (a) `RunManager` 类体**禁止任何 `RunStatus` 类型字段，或 `dict[<run_id> → RunStatus]` 类型字段**（无论命名；语义判断覆盖 `_status_cache` / `_run_status` / `_statuses` 等任意命名）。
  - (b) `discover_runs` 函数体未被 `functools.cache` / `functools.lru_cache` 装饰；status 派生仅在 `_summary_from_tape` / `_meta_from_handle` 内即时计算。
  - (c) **显式豁免**：`_scan_meta_overview_cached` / `_meta_cache` 缓存的是 overview（含 `run_status` 字段的超集 dict），属 perf 优化且删了能从 tape 完全重建，合 C5「cache 非 index」契约（run_manager.py:1479-1481）——不视为第二真相源。豁免理由：overview 是 tape 的纯投影，可重建，无独立写入路径。

### AC12 — 回归测试枚举（E1）

- **断言**：以下既有测试文件中所有以 `discover` 命名的测试（实现期 `grep -r discover tests/iface/web/` 出具清单写入 release note）必须保持 green：
  - `tests/iface/web/test_run_manager.py::discover*`（如 `test_discover_runs_*`）
  - `tests/iface/web/test_multi_run_phase_c.py`（含 discovery 相关用例）
  - 实现期 grep 出的其他 `discover*` 测试（若有）
- **强制**：实现期 release note 必须列出 grep 出的具体测试函数清单，证明全部 green（防止遗漏 silent skip）。

### AC13 — 破坏性变更 release note 强制（E4）

- **断言**：`docs/releases/<date>-audit-e.md` 存在；其内容命中关键词集 {`legacy tape 缺失`, `skip`, `started_at 语义`, `workflow_started.timestamp`, `crashed legacy`, `live-pending`（或 `running`）}（对应 §10 三条破坏性变更）。
- **理由**：§10 三条破坏性变更均标「release note 必须」，无 AC 强制则可能漏写。

## 7. 失败路径（fail loud）

| 场景 | 行为 | 出处 |
|---|---|---|
| legacy tape 文件不存在（绝对路径但缺失） | warn + skip（不伪造 status） | AC4(a) / 铁律 4 |
| legacy tape_path 是相对路径（即使 cwd 下有同名文件） | warn + skip（视为不可定位） | AC4(b) / 开放项 4 |
| legacy tape 内容乱码 / json.loads 失败 | `_summary_from_tape` 补 warn（**N1 修复点**，1612-1613）→ warn + skip；至少 1 条 warning 含 `run_id` + tape path | AC5 / N1 |
| legacy tape 0 有效事件（空文件 / 刚创建） | `_summary_from_tape` 返 None → skip | 1614-1616 现有 |
| legacy tape 无 workflow_started | `_summary_from_tape` 现有行为：wf_name 退化到 `tape_path.stem`（1619），run_status 缺省 `pending`（1621）→ status `live-pending`；不抛 | 1617-1632 现有 |
| `_list_legacy_metas` 整体失败 | 1410-1411 现有：catch + 空 list + 不崩 discovery | 保持 |
| `lm.run_id`（任一来源）与 tape_path.stem 不一致 | 以 tape_path.stem 为准（tape 是真相），记 warning（消息含 meta run_id + tape_stem） | C1 / AC10 |

**禁止**：任何路径下静默 fallback 到 `status="cancelled"` 字面量。

## 9. 实现期开放项（spec 不强约束）

1. **workflow_name 退化**：legacy 无 workflow.yaml 副本时，`_summary_from_tape` 走 `tape_path.stem`（1619）。是否需要保留原 `yaml_path.stem`（1423）作为更友好 fallback？实现期决定（传 hint 参数 or 接受 stem 退化）。倾向接受退化——DRY 优先，workflow_name 不是真相关键字段。
2. **legacy tape 缺失由「展示 stale 行」改「skip」是破坏性 user-facing 变更**（U2=a）：原代码 1418-1419 注释「仍展示（前端可看到 stale）」，但其 status 撒谎（硬编码 cancelled）；走 `_summary_from_tape` 后 tape 缺失 → skip + warn（C4 fail loud 优先；新增非 tape-derived status 值违铁律 1，主审推荐 skip+warn）。**这是破坏性 user-facing 变更**，release note 必须强制声明：用户在 discovery 列表将看不到 tape 缺失的 legacy run（如需 stale 可见性，应在前端单独处理，discovery 的职责是展示真相不是展示 stale）。
3. **E-2 是否升级到方向 B / C**：等实现期判断窗口是否实际造成 bug。spec 默认方向 A。
4. **legacy tape_path 假定为绝对路径**：若 BgRunMeta 的 `tape_path` 是相对路径，resolve 后仍可能落到 cwd 而非原始 spawn 目录。开放项决策：相对路径走 AC4 的 warn + skip 分支（视为不可定位）。实现期验证相对路径是否真实存在（若历史 BgRunMeta 一律写绝对路径，则该分支永不触发，仅作防御）。

## 10. 与既有契约的相容性核对

| 既有契约 / 行为 | 本 spec 是否触动 |
|---|---|
| `_summary_from_tape`（1593-1657）派生口径 | 不改派生逻辑，复用；**例外**：内层 except 补 warn（N1） |
| `_scan_meta_overview_cached`（1469-）三层缓存 | 不改，`_summary_from_tape` 内部已走它 |
| `handle.status` 在 cancel 路径（1101、1131）的作用 | 不改（E-2 方向 A 仅文档化） |
| `_meta_from_handle`（1210-1255）progress/cost 从 tape | 不改（status 仍取 handle.status，但 docstring 显式化 hint） |
| 铁律 1（唯一真相源） | **强化**：消除 legacy 字面量分支 |
| 铁律 2（一条读路径） | **强化**：legacy 走同款 `_summary_from_tape` |
| 铁律 4（fail loud） | **强化**：tape 缺失/损坏 warn + skip，不伪造 |
| DRY | **强化**：消灭双派生口径；三分支共享 `seen_ids` dedup |
| 依赖单向（events → schema） | 不触动（discovery 在 iface 层，依赖 events 合法） |
| **🚨 破坏性 user-facing 变更 (a)**：legacy tape 缺失 | 原行为：展示 stale 行（status 硬编码 cancelled）。新行为：**skip + warn**，列表不再展示该 run。**release note 必须声明**。理由：消除伪造 status（违铁律 1）。如需 stale 可见性应在前端单独处理。 |
| **🚨 破坏性 user-facing 变更 (b)**：legacy `started_at` 语义迁移 | 原行为：`started_at` 取 BgRunMeta.started_at（spawn 时刻）。新行为：走 `_summary_from_tape` 后取 tape `workflow_started.timestamp`（emit 时刻）。两者秒级差异（spawn → emit 之间有 cli 启动 / tape open 间隔），前端按 `started_at` 排序的顺序可能变化。**release note 必须声明**。 |
| **🚨 破坏性 user-facing 变更 (c)（E9）**：crashed legacy run（tape 无终态事件）显示 | 原行为：硬编码 `cancelled`。新行为：从 tape 派生 → `live-pending` 或 `running`（按 `_summary_from_tape` 的 `overview.run_status` 映射）。**Trade-off（接受）**：新行为可能比 `cancelled` 更误导——用户看到 `running`/`live-pending` 可能 attach 一个实际已死/崩溃的 run，需手动清理。**接受理由**：tape 真相 > 用户感知便利（铁律 1 优先），伪造 `cancelled` 违铁律 1 且掩盖 crash 信号（违铁律 4）。**release note 必须声明**，建议同时给出「crashed legacy run 手动清理步骤」。 |

---

**结语**：E-1 是必须修的真裂缝（字面量取代 tape 派生，直接违反铁律 1，用户可观察后果严重——误重跑 / 掩盖 crash）。E-2 是设计 trade-off 的边界未显式化，文档化即可。两者都不需要改 events 层，scope 局限在 `run_manager.py` 的 discovery 路径。
