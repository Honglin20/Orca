## 1. 背景与根因

### 1.1 为何 fail loud 是铁律

CLAUDE.md 规则 12 **Fail loud**：边界、空值、失败路径显式处理，**不静默吞错**；报错处理必须用户可见（"重试中 / 第 N 次 / 失败原因"）。

前端是 Orca 整条事件链的**最后一公里**：`tape → bus → ws → store fold → selector → React render → 用户眼睛`。任何在 store/hook 层的静默吞错，都会让后端真相**对用户不可见**——用户看到的是空白页/虚假的"暂无图表"，而不是「loadRun 失败 HTTP 500」。在 Orca 单 tape 真相源架构下，**前端静默吞错 = 真相链断裂**：tape 完整、bus 正常、WS 推送了，但用户看到的是错误的状态，且无法自救（无重试入口、无错误提示、刷新无效）。

这正是 `workflow-store.ts` 当前状态：docstring line 100 自吹「失败 fail loud」，**实际四处 loader 全是 `console.error + return`**——零错误态、零重试、零 UI 提示。这是文档撒谎（违反规则 12 与"产品说明书不撒谎"原则）。

### 1.2 Bug2 根因链（CRITICAL）

CURRENT.md 记录的 Bug2「同 session 第二次 run 前端永久空白」前端根因：

```
用户切到 /runs/<id2> → useRunEvents(runId) mount → loadRunWithMeta(id2)
  → fetch /api/runs/<id2>/events  返回非 200（任何瞬时错误：后端重启 / race / 500）
  → console.error(...) + return           ← 静默吞
  → store 无 loadError / loading 字段
  → RunDetailPage 只读 s.status，不读任何错误态
  → 页面渲染空白（events=[] 派生全空）
  → use-run-events useEffect 只 mount 一次，无补救
  → 永久空白，刷新页面才有可能恢复
```

**关键证据**：`run-list-store.ts:39-50` 已经有规范的 `loading / error / lastFetch` 三件套；`workflow-store.ts` 完全没有。两个 store 同一项目、同一作者、同一 SPEC 体系，前者 fail loud、后者静默——证明这是**实现遗漏**而非设计选择。

## 3. 不变式 / 契约

### INV-1 后端错误必须用户可见（fail loud）

loader **终态失败**必须写入 store 错误态 + UI 渲染错误提示（含失败原因 + 「重试」入口）。**禁止** `console.error + return` 形式的静默吞错。`console.*` 仅作开发日志，**不**作为用户可见通道。

**qualifier（M9）**：中间探测允许 silent 降级——`/meta` 失败可 silent fallback 到 `/events` 全量路径（已是当前行为）；**但 full 路径也失败 → 必须串到错误态**（不得二次吞）。

### INV-2 reducer 幂等是 dev-mode 自检，prod 不强制（U1 降级）

handler 表语义幂等性**理想是不变式**，但当前 `agent_usage.cost +=` / `reasoningTokens +=` / `foreach_item_completed` 等是累加语义，改造为 last-writer-wins 涉及 tape 契约解读，**defer 到独立 follow-up**（§5.2）。本 SPEC 仅加 dev-mode 自检（prod no-op，仍是君子协定）——**显式承认**当前幂等靠调用方 seq 去重，不是 reducer 层硬不变式。

### INV-3 长 run 不卡主线程

`processEvent` hot path 必须是 O(log N) 或 O(1)，禁止 O(N)。**真 oracle**：单帧 < 16ms（60fps 不掉帧）。基准 fixture（§6 AC12）下绝对值 < 500μs/事件 或 旧 O(N²) → 新 O(N) 速度 > 10x。

### INV-4 状态切换原子化（half-loaded 仅指 throws 中 / 非 array JSON）

loader 抛异常（如 `resp.json()` parse throw）**或返回非 array JSON**（`!Array.isArray(json)`）时 store **不得**留下 half-loaded 态，归错误态 `kind="parse"`。**half-loaded 定义**：`activeRunId` 已写 + `loadFromEvents` 未提交（throws 中）。

**澄清（M7/G7）**：`events === []`（后端 race / live-pending）**合法**——web-attach §7 允许 live-pending 空 events，UI 显示 idle（空会话）非错误。INV-4 仅覆盖 parse-throw / 非 array JSON / 中间步骤 throw 路径。

### INV-5 schema 漂移必须显形（仅 chart_type / data-shape；kind-rename 出范围）

chart payload 不符合契约（**缺 `chart_type` / `data` 非 array**——shape 漂移）**不得**被 silent filter 掩盖成「暂无图表」。必须以可见方式提示「N 个 chart 解析失败」——让后端契约违背对开发者可见。

**出范围（M5/U3）**：`data.kind` 字段重命名（kind-rename）漂移**不可由前端探测**（无 kind 注册表），归 §5.2 follow-up。

### INV-6 单点崩溃不连累整 tab

recharts 或任何 chart widget 抛错 **不得**冒泡卸载整个 charts tab。必须由 ErrorBoundary 兜底，显示「该 chart 渲染失败」+ 保留其他 chart 可用。

### INV-7 loadStatus 非 loaded 时拒收 WS 增量 + defer-RESUME（M13 / C1 / E1 round-4）

`loadStatus !== "loaded"` 时 `processEvent` **拒收** WS 推送的增量事件（drop + 模块级 warn-once Set，E6）。

**defer-RESUME（E1 round-4 BLOCKER，纠正 rev4 错误假设）**：rev4 的 defer-**subscribe** 不管用——实读 `ws_handler.py:266-308 _handle_subscribe` 仅 `handle.bus.subscribe()` 不读 tape；`bus.py:218` docstring 明示「新订阅者只收订阅之后 emit 的事件」。subscribe forward-only → `(fetch_commit, subscribe_send]` 窗口事件仍永久丢。subscribe_time > fetch_commit_time 只能防重复不能防 gap。

**解决方案（决策 E1，defer-RESUME）**：initial-load **loaded 后发 `sendResume since=lastSeqSeen`**（非 sendSubscribe）——server 经 `ws_handler.py:192-264 _handle_resume` 从 tape 重放 `seq>lastSeqSeen` 后再 subscribe（`_handle_subscribe`），补全 `(fetch_commit, sendResume_send]` 窗口事件。reconnect 路径 `sendResume` 不变。

**use-websocket 调用契约（spec 显式声明，E2 round-4 / BLOCKER-2 + A1/A2/A4/A5 round-5）**：本 SPEC 触及 `use-websocket.ts` 订阅生命周期。`use-websocket.ts:214` 当前 deps 是 `[runId, processEvent]` 不响应 loadStatus——钉死改造：

- **listener 在 useEffect 顶层注册一次（BLOCKER-2，非 onopen 内）**：onopen（use-websocket.ts:139）是**多次触发的 reconnect 事件**，在 onopen 内注册 listener 会随 reconnect 累积 → 内存泄漏 + 旧 socket 引用残留重复 sendResume。改造：`const unsub = useWorkflowStore.subscribe(listener)` 在 useEffect 顶层注册一次；listener 闭包经 **ref / module 变量**读当前 socket（不闭包旧 socket）；**首次到 loaded 后 sendResume + `unsub()` 自清（one-shot, A4）**；useEffect cleanup 调 `unsub()`。
- **onopen 内只读 `getState().loadStatus` 决定立即 sendResume vs 等回调（BLOCKER-1 round-6 重写）**：**loaded 或 error → 立即 sendResume**（两态 sendResume 均安全——loaded：lastSeqSeen=当前 events 最大 seq；error：lastSeqSeen 或为同 run 上一个 loaded 残留值，或为切 run 时 `unloadRun`→`resetDerived` 清的 0，since=0 即全量重放无 dup，since=stale 即部分补全无 dup）；**loading/idle → 等回调**（listener 仍 active，首次 loaded 翻转时 fire）。**此规则使 §3 与 §7 reconnect 行一致**——listener 路径只适用 initial loading→loaded race（listener 仍订阅时）；error→loaded 翻转后的 retry 由 §7 reconnect onopen 读 error 立即 sendResume 兜底（不依赖 listener，因 listener 已 one-shot 自清）。
- **reconnect × loadStatus 优先级（round-7 F1 闭环）**：`wasReconnect`（socket 维）与 `loadStatus`（store 维）正交，spec 钉死优先级 = **loadStatus 优先**。即 reconnect onopen **先读 loadStatus**：loaded/error → 立即 sendResume + sendSubscribe 双发（§7 reconnect 路径，server-restart 韧性）；loading/idle → **不双发**，仍走 listener 路径（仅 sendResume，因 loading 期 server 一般未重启，lazy-mount 不需要）。两种实现行为一致由 AC22 negative case 钉死（mock reconnect during loading → `socket.send type:"subscribe"` 调用次数 === 0）。
- **per-socket resumeSent dedup（MAJOR-2 round-6，必加）**：onopen 立即 sendResume 与 listener fire sendResume 同 socket 可能 race（onopen 触发后 listener 也观察到 loaded 翻转）→ 两次 `_handle_subscribe` → server `_handle_subscribe:298` cancel-then-resubscribe await yield 期间事件丢（A5 想消除的风险被双 fire 重新引入；readyState guard 不够因两次都在同 OPEN socket）。改造：每个 socket 实例维护 `resumeSent: boolean` closure 变量（reconnect 随新 socket 重置）；onopen 与 listener 共用此标志——已 sendResume 则另一方 no-op。
- **listener 形式（A1 round-5）**：zustand 无 `subscribeWithSelector` middleware——`useWorkflowStore.subscribe(listener)` 是**全 state listener**（listener 接收完整 state）；listener 内部 diff `prev.loadStatus !== curr.loadStatus && curr.loadStatus === "loaded"` 判定翻转。**不引 middleware**（simplicity，避免改动 store 构造）。
- **reconnect 路径 sendResume + sendSubscribe 顺序（MAJOR-3 round-6，部分 reverse A5）**：rev6 A5「reconnect 仅发 sendResume」**引入 server-restart 回归**——实读 `ws_handler.py:213-216 _handle_resume`：`handle = get_handle(run_id); if handle is None: warn + return` 在 L245 `_handle_subscribe` **之前 short-circuit**，即 run 未 attach 时 `_handle_resume` **不 subscribe、不 lazy-mount**；唯一 `ensure_attached`（lazy-mount from discovery）路径在 `_handle_subscribe:277-292`。server 重启 → in-memory handle 丢失 → client reconnect 仅发 sendResume → `_handle_resume` warn「未知 run_id」return（无 subscribe 无 replay）→ client stuck。**修正**：reconnect 路径**保留 sendSubscribe 作 server-restart fallback**；顺序 = **sendResume 首帧**（首帧优先重放历史，handle 存在时 server 经 `_handle_resume` L245 内部 subscribe 接 live 流）+ **sendSubscribe 次帧**（仅当 server 不识别 resume / 重启后无 handle 时，由 `_handle_subscribe:277-292` lazy-mount from discovery）。
- **冲突 surface（Rule 7，不 average；round-7 F2 闭环 rationale）**：保留 sendSubscribe 保 server-restart 韧性，**代价**是 server 端 `_handle_subscribe:298` 两次调用（`_handle_resume` L245 内部一次 + 显式 sendSubscribe 一次）之间的 cancel-race 窗口——**此窗口 inherent to 双发设计，不由 MAJOR-2 per-socket resumeSent 缓解**（resumeSent 仅 dedup sendResume 帧；sendSubscribe 仍发，server 端两次 subscribe 之间 `await _cancel_sub` yield 期 bus.emit 事件理论上可能丢）。client 端不重复发 sendResume 由 BLOCKER-2 one-shot listener 保证（reconnect 时 listener 已自清，listener 路径不参与）。race 窗口极小（两次 subscribe 同 tick 内顺序处理；ws_handler 每 ws 串行处理消息），且 server-restart 韧性收益 > 理论 race 损失，按 Rule 7 接受。**实现者勿误以为 resumeSent 已覆盖此 server race 而放松 server 端 `_handle_subscribe` 的 cancel-then-resubscribe 健壮性**。
- **initial-load 路径不双发（与 reconnect 区分）**：initial mount 的 listener fire 仅发 sendResume（不 sendSubscribe）——initial mount 时 server 必有 handle（同一 process 起的 run）或 ensure_attached 已被 list/attach 触发；不涉及 server-restart 场景。
- **loadStatus 翻转时 socket 已断开的补发窗口（A2 round-5）**：listener 触发 sendResume 时若 socket 不可用（onclose 期）→ 该 sendResume 失败（socket.send throw catch）→ 由 **reconnect 路径 sendResume + sendSubscribe 兜底**（reconnect onopen 读 loadStatus=loaded/error → 立即 sendResume + 次帧 sendSubscribe）；延迟 = backoff（1s/2s/.../30s）。simplicity：不新增 fallback。
- reconnect 既有 sendResume watchdog + triggerResumeFallback 也保留（C10/E7）。

**理由（G1）**：retry 成功路径走 `loadFromEvents` **全量重拉**（`loadRun` / `loadRunWithMeta` / `loadFull` 均重 fetch events），被 INV-7 drop 的事件由**重拉**补回；non-retry 场景由 defer-RESUME 补全。**不再依赖** socket reconnect 的 sendResume（虽 reconnect 路径仍用）。

**例外（G5）**：`loadEarlierChunk` 前置 `state.huge === true` 隐含 `loadStatus === "loaded"`，走 `set + refold` 路径不经 `processEvent` 入口，INV-7 不拦。

**use-websocket triggerResumeFallback 交互（C10/E7）**：实读 `use-websocket.ts:71-96`，`triggerResumeFallback`（3s watchdog 触发的独立全量重拉）调 **public `loadFromEvents`** action。**显式不变量（E7 round-4）**：public `loadFromEvents` action 签名与 loadStatus 行为**保持不变（不 touch loadStatus）**——它是 WS resume-fallback 路径专用；本 SPEC 的 `loadRun` / `loadRunWithMeta` / `loadFull` 内联私有 `_refoldAndCommit` helper（不调 public `loadFromEvents`），避免 triggerResumeFallback 误翻 loadStatus。triggerResumeFallback 自身的 fail-loud 改造（L77-92 仍 console.error+return）out-of-scope，标 follow-up。

**INV-7 warn-once（E6 round-4）**：drop 用模块级 `Set<string>` 记 `runId::seq`，drop 时 add + warn-once（同 seq 第二次 drop 不重复 warn）；`unloadRun` 清此 Set。

**原子性（N5/C12）**：`loadStatus = "loaded"` 翻转与 events 写入在**同一 `set` 调用内**（§4.5 per-attempt 原子提交），不存在 loaded 但 events 未提交的窗口。

## 4. 方案（方向级，不写完整代码）

### 4.1 C1 修复 —— 加 loadStatus / loadError / retryCount + 用户可见退避重试 + 重试取消 + 错误态 UI

**store 层**（`workflow-store.ts` + `store-types.ts`）：

- `WorkflowState` 新增字段（与 `run-list-store.ts:42-44` 对齐）：
  - `loadStatus: "idle" | "loading" | "loaded" | "error"`（**初始 `idle`**，M18）
  - `loadError: { kind: "http" | "network" | "parse"; status?: number; message: string } | null`
  - `retryCount: number`（**进 store**，E4 round-4：驱动 reactive banner；loader invocation 入口 `set({retryCount:0})` 显式 reset 防 B 继承 A）
  - `historyLoadError: boolean`（**单开关**，M14；不是 N 个 chunk 的计数）
- 三处关键 loader（`loadRun` / `loadRunWithMeta` / `loadFull`）+ 一处历史 loader（`loadEarlierChunk`，免重试，见下）改造：
  1. 进入时 `loadStatus = "loading"` + `loadError = null` + `retryCount = 0`。
  2. 非 200 / 网络错误 / parse 失败（含 `resp.json()` throw **或** `!Array.isArray(json)`，G7）→ 进退避序列；3 次失败后 → `loadStatus = "error"` 终态 + 写 `loadError`（`kind="parse"` for parse 类）。
  3. **退避重试（关键 load 三处，BLOCKER-3 round-5）**：3 次指数退避（1s / 2s / 4s），**退避期间 loadStatus 保持 `loading`**（不加 retrying 状态，LoadStatus union 不扩）；每次 `set({retryCount: n})` 驱动 reactive banner（E4）；UI 在 loading 骨架上方**叠加非阻塞 retry-banner** 显示「重试中 第 N 次」+ 失败码（用户可见通道）；`console.warn` 仅 dev log；3 次仍失败 → `loadStatus = "error"` 终态。**手动重试按钮仅在终态 `error` 渲染**（与 BLOCKER-3 配套，防退避中双重 fetch）。**loadEarlierChunk 免重试（C6）**：历史拉取非关键 load，失败仅 set `historyLoadError=true` + banner，不进退避序列。
  4. 成功 → `loadStatus = "loaded"`（关键 load）+ `set({retryCount: 0})` reset。
  5. **手动重试（M10/E4/C3）**：**仅**终态 error 后用户点「重试」按钮（loading 期间不渲染按钮）→ 新 invocation，`set({retryCount: 0})` 重置 → 重进 3 次退避。
- `loadRunWithMeta` 的 `/meta` 失败（L570）保留 silent fallback 到 full 路径（INV-1 qualifier 允许）；full 也失败 → 必须串错误态。
- `unloadRun` 复位 `loadStatus = "idle"` + 清 `loadError / retryCount / historyLoadError / seenSeqs` + abort-all + Map 清理（M18）。

**退避状态机 UI 渲染表（BLOCKER-3 round-5）**：

| loadStatus | retryCount | 渲染 |
|---|---|---|
| `idle` | 0 | 骨架（同 loading 视觉，M18） |
| `loading` | 0 | 骨架 |
| `loading` | >0 | 骨架 + 非阻塞 retry-banner 叠加（无重试按钮） |
| `error` | 任意 | 错误态 + 重试按钮（无 retry-banner） |

**retryCount 语义（E4 round-4，推翻 C11）**：retryCount **进 `WorkflowState` store**——是 reactive banner 的真相源（local closure 无法驱动 React 重渲染）。loader invocation 入口 `set({retryCount: 0})` 显式 reset 防 B 继承 A；退避循环 `set({retryCount: n})` 驱动 banner。store-types.ts 加 retryCount。

**重试取消机制（B2 + G2/N2 + C2/C3/C4 round-3，必加）**：

- **Map 而非 WeakMap（C3）**：模块级 `Map<runId, { abort: AbortController, timer: ReturnType<typeof setTimeout> | null, epoch: number }>`（**WeakMap 键必须对象，runId 是 string 不可能**）。清理时机：`unloadRun` 调 `map.delete(runId)`；load 同 runId 时覆盖（新 entry）。**schedule 退避 timer 时同步 `entry.timer = timer`（C1 round-5）**——abort-all-entries 的 `clearTimeout()` 才能取消 pending 退避，否则 timer 脱离 entry 成孤儿。
- **fetch 全部带 signal（G2 钉死，含 retry fetch — C12）**：三处关键 loader（含其 retry 循环）+ loadEarlierChunk 的**所有** fetch 调用必须 `fetch(url, { signal })`，signal 来自当前 runId 对应 entry 的 `abort`。abort 时 in-flight fetch 立即 reject（`AbortError`）。
- **abort-all-entries（C2/E9）**：任一新 `loadRunWithMeta` / `unloadRun` 调用 → **iterate 整个 Map**（不只同 runId），每个 entry `abort() + clearTimeout() + map.delete(...)`。理由：loadEarlierChunk(A) 在飞时切到 B，per-runId abort 不动 `map[A]` → A chunk 解析后 L636-646 无校验 set+merge+refold 污染 B（**Bug2-class 写污染**）。**顺序（E9）**：`moduleEpoch++` BEFORE iterate-abort——closure `myEpoch` entry 时固定，顺序无关（evaluator 已证），但 spec 钉死此顺序避免实现歧义。
- **loadEpoch 钉死一种语义（C4，模块级 counter）**：模块级 `let moduleEpoch = 0`，每次 loader invocation 自增 + closure 持有 `myEpoch = moduleEpoch`。**非 store 字段，store-types.ts 不加**。所有 `set(...)` 写入前**双重校验**：`get().activeRunId === expectedRunId && moduleEpoch === myEpoch`——不一致则丢弃。
  - **Bug2 同根变体（N2）**：A→B→A 快切场景，第一次 load(A) 的迟到 fetch（无 signal 未中断）在切回 A 后 resolve，仅靠 `activeRunId === A` 校验**通过**（同 runId）→ 陈旧结果污染第二次 load(A)。`moduleEpoch` 区分同 runId 不同实例。
  - 删除 rev3 中"per-runId entry epoch / store 字段 get().loadEpoch"两种矛盾措辞。
- **loadEarlierChunk 写时校验（C2，必加）**：loadEarlierChunk entry 持 `epoch`（originating load 的 epoch），resolve 后写入前**双重校验** `get().activeRunId === originatingRunId && moduleEpoch === myEpoch`——不一致则丢弃。INV-7 例外（L143）显式排除 loadEarlierChunk，但写时校验仍需加（INV-7 排除的是 processEvent 入口拦，不是写入校验）。
- 防止「比现状更糟」：当前无重试无串话风险，加退避重试若不取消，切 run 时 A 的 timer/fetch 会写脏 B 的 state。

## 7. 失败路径

| 失败场景 | 行为 | 用户可见 |
|---|---|---|
| `/events` 非 200 | **退避期间 loadStatus 保持 loading**，retryCount>0 叠加 retry-banner（BLOCKER-3）；3 次失败翻 `error` 终态 | loading+retry-banner（无按钮）→ error 终态 + 重试按钮 |
| `/events` 网络错误 | 同上 | 同上 |
| `/events` 返回 malformed JSON | parse throw / 非 array JSON 归 parse 类 → 错误态（INV-4 不留 half-loaded） | 同上 |
| `/meta` 非 200（huge 判定） | silent fallback 到 full 路径（INV-1 qualifier 允许）；full 也失败 → 错误态 | 错误组件 |
| `loadEarlierChunk` 失败 | `historyLoadError=true` + 节流 + **免重试**（C6：历史拉取非关键 load） | 非阻塞 banner；下次成功自动清 |
| 重试 3 次仍失败 | loadStatus 翻 `error` 终态，等用户手动点「重试」（仅 error 态渲染按钮，BLOCKER-3；reset retryCount=0） | 错误组件 + 重试按钮（无 retry-banner） |
| chart payload 异常（shape 漂移） | partition + 警告条 + 正常 chart 仍渲染 | 警告条 |
| chart widget 抛错 | ErrorBoundary 兜底，单 chart 失败 | 单 chart fallback |
| foreach progress 形异常 | silent skip → warn + 保留原值 | progress 保持原值（UI 不显示 NaN） |
| 切 run 时前 run 退避 timer pending / in-flight fetch | cancel timer + abort-all-entries（iterate 整个 Map）中断所有 in-flight fetch（C2） | 无串话（G2/N2/C2） |
| loadEarlierChunk(A) 在飞 + 切 B + A chunk late-resolve | 写时校验（activeRunId/moduleEpoch）丢弃，不污染 B（C2 BLOCKER） | 无视图污染 |
| A→B→A 快切同 runId 不同实例 | moduleEpoch 校验丢弃陈旧 resolve | 无污染（N2/C4） |
| initial load 时 socket 比 fetch 先连 + server 推 seq=N+1 | INV-7 因 loading drop + **defer-RESUME**（loaded 后发 sendResume since=lastSeqSeen）→ server `_handle_resume` 重放 N+1 → fold（E1 BLOCKER；subscribe forward-only 不管用） | 无可见事件丢失 |
| loadStatus 非 loaded 时 WS 推事件 | drop + warn-once（模块级 Set<runId::seq>，E6） | 无可见变化（loaded 后由 sendResume 全量重补 / retry 全量重拉，非依赖 plain subscribe；G1/E1） |
| socket reconnect 期 loadStatus="error" | reconnect onopen 发 sendResume since=lastSeqSeen → server 重放 seq>N → INV-7 暂拒收（loadStatus 仍 error）；retry 成功 loadFromEvents 重建 lastSeqSeen → 后续 WS 增量正常 fold（E8） | 错误组件保留至 retry 成功 |
| reconnect onopen 帧（A5 → MAJOR-3 round-6 reverse） | reconnect 发 **sendResume 首帧**（重放历史 + handle 存在时 server 内部 subscribe）+ **sendSubscribe 次帧**（server-restart handle 丢失时由 `_handle_subscribe:277-292` lazy-mount from discovery）；rev6 A5「仅 sendResume」会引入 server-restart stuck 回归，必须保留 sendSubscribe fallback | 无可见变化（双发由 MAJOR-2 per-socket resumeSent dedup 缓解 client 端 race） |
| reconnect-during-loading + server-restart 三联（round-7 F3 文档化） | reconnect 发生在 initial loading 期 + 同时 server 重启（in-memory handle 丢失）→ onopen 读 loadStatus=loading → 等回调（不双发）；listener fire 仅发 sendResume → server `_handle_resume:213-216` short-circuit（handle=None）不 lazy-mount → client stuck 至 3s resume watchdog 触发 triggerResumeFallback；若 server 重启后 `/events` 路由也无该 handle 则 fetch 404，等用户手动重试 | 短暂 stuck（≤3s + backoff），用户手动重试恢复；频率极低（三联边缘），按 Rule 7 simplicity 接受，不增 fallback |
| loadStatus 翻转时 socket 已断开（A2） | listener sendResume 因 socket 不可用失败 → 由 reconnect 路径 sendResume 兜底；延迟 = backoff（1s/2s/.../30s） | 用户感知 = 短暂延迟，事件最终补全 |
| Bug2 场景（切 run 后失败） | 错误态显示 + 切回上一个 run 正常 | 错误组件 |
