# SPEC D —— 并发 / 守护进程竞态（audit 聚类 D）

> 类型：**补强型**（不改核心架构、不动单 tape 唯一真相源、不引入第二 registry）。修 4 处真实并发竞态 / 跨进程不可移植 / 静默吞错。其中 finding 1 是 **架构性问题**（auto-exit 决策权限越界到 process lifecycle，撕掉并发 run），其余 3 条是 **bug**（局部错误处理 / 平台分支缺失）。

## 1. 背景与根因

Orca 的 web 后端有两条独立的「并发 / 守护」链路：

- **进程内并发 run**：`RunManager`（`orca/iface/web/run_manager.py:221`）用 `max_concurrent=3` 的 `Semaphore` 真并发跑多个 in-process run；`orca run` web-default 路径（`commands.py::_serve_and_run_inprocess`）只是把**自己 start_run 的那个 run** 当作「主 run」来 await + auto-exit 触发。
- **跨进程 detached 守护**：sidechain 守护（`sidechain_daemon.py`）通过 pidfile + `_daemon_liveness.pidfile_daemon_alive` 做存活探测；spawn / respawn 决策由 `_ensure_sidechain_daemon` 在每次 `orca next` 时调。

这两条链路目前都有竞态/不可移植/静默吞错缺陷，聚类为 D。它们的共性是「单点决策者拿了不全的信息做全局决策」：

- finding 1：auto-exit 决策者只看主 run 终态 + 主 run 的 WS，看不到 `RunManager._runs` 里其他并发活 run。
- finding 2：pidfile 写/删不带 ownership，A 退到 finally 会删 B 的 pidfile。
- finding 3：liveness 探测写死 `/proc`，macOS 永远判 dead。
- finding 4：`_on_run_changed` 控制帧 QueueFull 静默丢，与同文件其它三处 warning 不一致。

```python
    h for h in self._runs.values() if isinstance(h, InProcessRunHandle)
]

    h._task for h in in_proc_handles
    if h._task is not None and not h._task.done()

    try:
        await asyncio.wait_for(asyncio.shield(task), timeout=timeout)
    except asyncio.TimeoutError:
        logger.warning("shutdown: run task %s %ss 未完成（可能卡在 gate），强制 cancel", ...)

```

`run_manager.py:221-229` —— `max_concurrent=3`、`_runs: dict[str, RunView]`、`_sem = asyncio.Semaphore(max_concurrent)`，允许同进程并发 3 个 in-process run。Web UI `POST /api/run` 走同一 manager → run B 与 A 真并发。

**竞态链（confirmed）**：A 起跑 → 用户在 web UI `POST /api/run` 起 B（`_sem` 允许） → A 终态 → `_wait_ws_autoexit` 启动 → 用户关浏览器 tab → `active_ws_count` 归零 → N 秒后 `_wait_ws_autoexit` return → finally `server.should_exit=True` → uvicorn lifespan → `manager.shutdown` 把 B 的 `_task` 当作"未完成的 pending task" `wait_for(timeout)` 超时 cancel。B 即便未终态、用户还想看，也被撕掉。

### 2.3 MINOR — liveness 写死 `/proc`，macOS 永远 dead（`_daemon_liveness.py:101`）

## 3. 不变式 / 契约

### 3.1 进程内并发 run 的生命周期契约

**I-1（auto-exit 不越权）**：`orca run` web-default 路径的 auto-exit 决策**只能由「该进程内所有 in-process 非终态 run 都已终态」触发**，不能仅凭「主 run 终态 + 无活跃 WS」触发。即：`_wait_ws_autoexit` 的退出条件必须包含 `manager 内无非终态 in-process run`。

**I-2（shutdown 只撕 dead/超时）**：`manager.shutdown` 的语义保持不变（lifespan 退出时收尾所有 run task，超时 cancel）——但被 auto-exit 触发时，I-1 保证此时已无活 run，`shutdown` 实际只跑 teardown 路径，不再有"撕掉 B"的副作用。

**I-3（`--stay` 显式覆盖）**：`--stay` 路径维持现状（serve 直到 Ctrl-C / 外部 should_exit），不受 I-1 影响。

### 3.2 pidfile 跨进程契约

**I-4（原子写）**：pidfile 写入必须 `tmp+os.replace` 原子语义，读端要么看到旧完整 pid、要么看到新完整 pid，永不读到 partial。

**I-5（ownership 校验 unlink）**：进程退出 finally 删 pidfile 前**必须**先读 pidfile 比对 `os.getpid()`；不匹配（说明已被更晚的守护覆盖写）→ **不删**，仅记 warning。守护 unlink 自己的 pidfile 是 ownership 行为，不是"清理路径"。

**I-6（保守 false 不变）**：`pidfile_daemon_alive` 的「保守 false」原则（docstring line 8-11）不动；macOS 分支只是把"非 Linux 一律 false"细化为"macOS 用 ps subprocess/kill -0 + cmdline 校验"。

### 3.3 控制帧 fail-loud 契约

**I-7（QueueFull 必 warn）**：所有把**帧 payload**（dict / event）`put_nowait` 入 WS queue 的路径，`asyncio.QueueFull` 必须 `logger.warning`（带 run_id / conn id / 帧类型），与同文件 `_pump` / `_handle_resume` 对齐。控制帧（`run_changed`）尤其不能静默——它承载 manager delete/cancel/attach 的真相对账。**例外**：`_cleanup`（`ws_handler.py:384`）的 `None`-sentinel 入队不在此列——sentinel 是 best-effort，紧接的 `writer.cancel()`（387-388）已强制停队列消费，`QueueFull` 时 sentinel 多余、`pass` 正确。

### 3.4 跨进程并发模型声明

| 资源 | 保护机制 | 现状 | 本 SPEC 后 |
|---|---|---|---|
| tape 文件 | `fcntl.flock`（`cli._flock_path`） | 已有 | 不变 |
| WS connection queue | 单 writer task 串行化（`_writer_loop`） | 已有 | 不变 |
| `RunManager._runs` | asyncio 单事件循环（无锁，单线程协作） | 已有 | 不变 |
| sidechain pidfile | **无锁**（裸 write_text + 盲 unlink） | 缺 | **tmp+replace + ownership unlink**（应用层原子，无需 flock） |
| pidfile 读端探测 | 无锁（只读） | 已有 | 不变（macOS 分支新增） |

pidfile 不引入 `flock`：tmp+`os.replace` 是 POSIX 原子语义，足够覆盖"读端看到完整 pid"；ownership 比对解决盲 unlink。flock 反而引入"守护 SIGKILL 不释放锁"的新问题。

## 4. 方案（方向级，不写完整代码）

### 4.1 finding 1（MAJOR，架构性问题）—— auto-exit 感知 manager 所有非终态 run

**问题分类判定**：架构问题。auto-exit 决策权限越界——它本应只回答"主 run 是否结束、用户是否还在看"，却单方面决定整个 uvicorn 进程的生命周期，从而撕掉它看不见的并发 run（`RunManager._runs` 中由 `POST /api/run` 起的 run B）。修复涉及 `_serve_and_run_inprocess` + `_wait_ws_autoexit` 的退出条件重定义 + 与 `RunManager` 的只读查询契约，属于"职责越界 + 数据流断裂"。**不允许打补丁**（比如只在 finally 里"如果还有活 run 就不 should_exit"——那会把进程永远卡住）。本 SPEC 是对齐方案。

**方案**：

1. 在 `RunManager` 上加只读 helper（不增加真相源，只是 `_runs` 的派生视图）：

   ```
   def has_nonterminal_inproc_runs(self) -> bool
   ```

   遍历 `_runs.values()`，返 `any(isinstance(h, InProcessRunHandle) and not h._task.done())`。**只读**，不锁、不改状态。依赖方向：`cli/commands.py` → `RunManager`（iface 内，单向，符合铁律）。**读 `h._task`（私有属性）与现有 `shutdown`（`run_manager.py:1181`）/ `wait_done`（1163）一致**——已是既存破口，本 SPEC 非新增封装破口，**勿改公有 property**（YAGNI，且改 property 会触动 InProcessRunHandle dataclass 形状）。

2. `_wait_ws_autoexit` 增加第三个条件（在原 `active_ws_count == 0` + `last_ws_activity_at` 超时之外）：

   ```
   AND not manager.has_nonterminal_inproc_runs()
   ```

   即：只要还有并发活 run，无论主 run 是否终态、无论是否有 WS，都**不**退出。`_wait_ws_autoexit` 签名加 `manager` 参数（或 `has_nonterminal` callable）。

3. `_serve_and_run_inprocess` 调用处把 `manager` 透传给 `_wait_ws_autoexit`。

4. `manager.shutdown` 语义不变（lifespan 退出兜底）；当 I-1 满足时被调，`pending` 自然为空，只跑 teardown。其它 `shutdown` 调用方（`_push_probe.py:1241` / `mcp/server.py:536` / `web/server.py:65` lifespan）**不受影响**——它们是有意 teardown pending task（进程要整体退出），本 SPEC 只保证 auto-exit 路径触发时 pending 为空。

5. `_wait_ws_autoexit` 第三条件阻挡退出时记 debug 日志：`auto-exit deferred: N non-terminal in-process run(s) still active`（每轮循环命中阻挡时记一次；N 由 `has_nonterminal_inproc_runs` 顺便返个数，或单独数）。便于 AC-1 验证 + 生产诊断「为什么 orca run 不退」。

**为什么不在主 run `await asyncio.shield(run_task)` 之后再加一段"等并发 run"？** 因为 auto-exit 的本意是"用户没在看就退"，并发 run B 用户可能正在另一 tab 看；强等 B 终态会 hang 进程。本方案的语义是「**有活 run 就不退**」，让用户继续看 B；用户全部关 tab 才触发退出。这与 `--stay` 区分清晰：`--stay` 是用户显式要常驻，本方案是"还有事在跑就别撕"。

**边界**：本 SPEC 不改 `RunManager.max_concurrent` 语义、不改 `POST /api/run` 路由、不改 `run_server` lifespan。仅修 auto-exit 决策条件。

### 4.2 finding 2（MINOR，bug）—— pidfile 原子写 + ownership unlink

**问题分类判定**：bug（局部错误处理，非跨模块抽象错位）。

**方案**：

1. 写 pidfile：`tmp = pidfile.with_suffix(".tmp"); tmp.write_text(pid); os.replace(tmp, pidfile)`。`os.replace` 是 POSIX 原子 rename，Windows 也原子（同卷）。
2. 退出 finally unlink 前：
   ```
   try:
       current = pidfile.read_text(encoding="utf-8").strip()
   except (FileNotFoundError, ValueError, OSError):
       current = None
   if current == str(os.getpid()):
       pidfile.unlink(missing_ok=True)
   else:
       logger.warning(
           "run %s: pidfile %s 已被其它守护覆盖写（current=%s, self=%s），跳过 unlink",
           args.run_id, pidfile, current, os.getpid(),
       )
   ```
3. 抽 helper（DRY）：`_write_pidfile_atomic(pidfile, pid)` / `_unlink_pidfile_if_owner(pidfile, pid)` 放在 `sidechain_daemon.py` 模块顶部（或 `in_session/_pidfile.py` 若 chart_daemon 复用）。**先 grep 确认 chart_daemon 是否同款问题**——若同款，统一抽公共 helper（DRY）；若 chart_daemon 用 socket 不用 pidfile，则本 helper 仅 sidechain 用。

### 4.3 finding 3（MINOR，bug）—— liveness 加 macOS 分支

**问题分类判定**：bug（平台分支缺失）。

**方案**：

`_daemon_liveness.py::pidfile_daemon_alive` 在 `/proc` 不存在时走 fallback。**确定路径（已 grep `pyproject.toml` 无 ps subprocess，不引新依赖）**：

1. **先** `os.kill(pid, 0)`（POSIX 通用，零 fork）。`ProcessLookupError` → False；`PermissionError` → 视进程存在（与 `/proc` 路径 PermissionError 行为对齐，进 cmdline 校验）。
2. **再** `subprocess.run(["ps", "-p", str(pid), "-o", "args="])` 取 cmdline 校验（防 pid 复用 + 防 zombie）。**用 `args=` 非 `command=`**——`args=` 保留 argv 空格边界，`command=` 可能截断/合并。
3. cmdline 匹配：输出 `strip()` 后做**子串匹配**（非 element-membership）：

   ```
   module_name in cmdline AND (run_id is None or ("--run-id" in cmdline and run_id in cmdline))
   ```

   守护 module_name + run_id 联合在 cmdline 中已足够唯一，子串跨参数误匹配概率可忽略（即便误匹配也只是多 spawn 一个守护，由 ownership unlink + 终态/TTL 自清）。

4. cmdline 不匹配 → False（pid 复用为其它进程 / cmdline 取不到）。
5. docstring line 18 的「POSIX-only」修正为「POSIX（Linux 走 /proc，macOS/BSD 走 ps）」。

**kill-0 ≠ 活（m3）**：zombie pid 仍响应 `kill(pid, 0)`。**cmdline 匹配 mandatory，禁止 kill-0 成功后 short-circuit `return True`**——必须再过 ps cmdline。

**fork-per-probe 成本声明**：原 `/proc` 路径零 fork（纯文件读），新 macOS/ps 路径每次 `orca next`（~10s 一次，非热循环）fork 一次 subprocess，可接受。可选缓解：按 `poll_interval` 秒 memoize 探测结果（同 pid + 同 pidfile mtime → 复用上次结果），非必须。

### 4.4 finding 4（MINOR，bug）—— `_on_run_changed` QueueFull 加 warn + 计数

**问题分类判定**：bug（fail-loud 一致性）。

**方案**：

`ws_handler.py:113-117` 改为：

```
except asyncio.QueueFull:
    logger.warning(
        "ws run_changed 控制帧 queue full (run=%s, action=%s, conn=%s) — dropping",
        run_id, action, conn.id,
    )
```

可选：在 `WebServer` 加 `dropped_control_frames` 计数器（`int`，`/api/health` 暴露），便于监控累积漂移。本 SPEC 仅要求 warn（与 `_pump` / `_handle_resume` 对齐），计数器为 nice-to-have。

## 6. 验收标准（可验证）

### AC-1（auto-exit 不撕并发 run）

**前置**：`orca run` web-default 路径，`max_concurrent=3`，浏览器已开。

**步骤**：
1. 起**短** workflow 作为主 run A（1 节点 5s 完成）——`_serve_and_run_inprocess` await 的就是 A 的 `_task`。
2. 浏览器在 `/runs/<A>` → `POST /api/run` 起并发**长** workflow B（含 sleep 30s 的 gate 节点），由同一 `RunManager._runs` 持有。
3. A 5s 后终态 → `_serve_and_run_inprocess` 越过 `await asyncio.shield(run_task)`（commands.py:1378）→ 启动 `_wait_ws_autoexit`。此时 B 仍非终态。
4. **关闭浏览器 tab**（`active_ws_count → 0`）。
5. 等待 `autoexit_seconds` × 2（远超单 run 退出窗口）。

**期望**：
- uvicorn 进程**不退出**（B 仍在跑）。
- `manager._runs` 中 B 的 `_task` 未被 cancel，B 继续推进到终态。
- 日志含 `_wait_ws_autoexit` 阻挡退出的 debug：`auto-exit deferred: 1 non-terminal in-process run(s) still active`。
6. **手动 cancel B 或等其终态** → `_wait_ws_autoexit` 第三条件满足 → N 秒后进程才退。

**负向 AC**：只要 `active_ws_count > 0`（用户在 B tab 看）→ 永不退（维持原契约）。

**为何角色这样分**：`_wait_ws_autoexit` 在主 run（被 `_serve_and_run_inprocess` await 的那个）终态后才启动。若主 run = 长，则启动时并发短 run 早已终态，`has_nonterminal_inproc_runs()=False`，第三条件永不触发——fix 等于没测到。主 run 必须是**短**，才能在 `_wait_ws_autoexit` 启动后仍留下一个非终态并发 run 验证第三条件。

## 7. 失败路径（fail loud）

- **`has_nonterminal_inproc_runs` 抛异常**（理论上 `_runs` 单事件_loop 不会，但防御）：在 `_wait_ws_autoexit` 内 `try/except` → 记 warning + 视为 True（保守不退，让用户自己 Ctrl-C，而非撕掉并发 run）。
- **pidfile tmp 写失败**（磁盘满 / 权限）：`OSError` → warning（沿用现有"探测会误判 dead 触发 respawn"语义），不阻断守护启动。
- **`os.replace` 失败**（跨设备——理论不会，tmp 与 pidfile 同目录）：raise（fail loud），让守护启动失败而非带病运行。
- **macOS cmdline 取不到**（ps subprocess 异常 / ps 命令异常）：保守视 dead（与原 `/proc` 路径 OSError 行为对齐），warning 提示「检查 ps 命令」。
- **`_on_run_changed` warn 自身异常**（logger 配置错）：被 `_broadcast_run_changed` 外层 `except Exception` 兜（`run_manager.py:1323`），不影响其它 listener。
- **并发 run B 卡 gate 永不终态（M1，行为变更必声明）**：`_wait_ws_autoexit` 第三条件永不满足 → 进程**不自动退**（预期语义：不撕活 run）。退出途径：Ctrl-C → `manager.shutdown` 对 B 的 `_task` `wait_for(timeout)` 超时 cancel。**行为变更**：修复前进程会在 `autoexit_seconds` 后退出并 cancel B；修复后不会。**release note 必须声明此变更**——用户若依赖"主 run 跑完进程自动退"来回收资源，长跑并发 run 会拖住进程，需手动 Ctrl-C。
