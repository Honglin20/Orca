## 1. 背景与根因

### 1.1 系统契约（不可破）

Orca 以 **单 tape 唯一真相源** 为底线（`docs/specs/phase-3-events.md` §1 反模式 ②/③/④）：
所有 run 状态都是 tape 的纯 reducer fold（`events/replay.py::apply_event`），live 与 replay 走同一条读路径。
Run 终态由三类互斥事件表达：`workflow_completed` / `workflow_failed` / `workflow_cancelled`（`orca/schema/event.py:22-24`，`replay.py:122-138`）。

由此推出两条不可破不变式：

- **I1 终态唯一性**：一条 tape 至多含一条终态事件。第二条终态事件 = tape 被污染。
- **I2 终态权威源在 tape，不在 marker**：marker 是 run 作用域的「宿主合规计数 + 句柄」缓存（`marker.py` 模块注释），其存在与否**不构成** run 是否活跃的权威判据。

### 1.2 触发路径

`orca stop` 在拿到 per-call flock 后**无条件** `bus.emit("workflow_cancelled", {"reason":"user_stop"})`（`cli.py:1774`），全程：

1. 不读 `RunState.status`；
2. 不扫 tape 是否已含终态事件；
3. 不查 marker 是否还代表活跃 run。

当 marker 因任何原因在 run 已终态后仍残留（emit 终态后被 SIGKILL / 断电 / `finally` 链异常 / 老坏 tape / 跨平台时序竞态），用户或主 session 调 `orca stop` 会向 tape 追加**第二条终态事件**，违 I1。

### 1.3 这是架构问题，不是局部 bug

判定信号（满足 ≥3 个不相关文件 / 跨模块契约错位，依 CLAUDE.md「问题分类」）：

- `cli.py` 的 `stop` 与 `orca/iface/web/run_manager.py::cancel_run`（`run_manager.py:1094-1113`）执行**同一语义**（用户取消 run → emit `workflow_cancelled`），但只有后者有终态短路守卫（`if handle.status in (...): return False`）。CLI 路径与 web 路径对同一不变式 I1 的守护**不一致** → 跨壳契约错位。
- 污染后果跨模块流窜：`events/replay.py`（状态折叠）、`iface/web/frontend/stores/workflow-store.ts`（web 状态机）、`iface/cli/widgets/log_stream.py`（TUI 渲染）、`iface/mcp/tape_index.py`（MCP 索引）—— 全部假设 I1。
- `cli.py:858` 的 docstring 把 marker 存在 ≡ run 活跃写成契约，但 marker 由 `finally` 链清（`cli.py:1784`），崩溃即破；同一份代码自相矛盾 → 抽象错位。

按 CLAUDE.md「问题分类」须先写 spec 对齐再改，不允许直接打补丁。

## 2. 现状证据（file:line，已实读核实）

### 2.1 MAJOR —— stop 无条件 emit（违 I1）

`orca/iface/in_session/cli.py:1766-1785`：

```
acquired = _try_acquire_flock(tape_path)            # 1766  拿 flock
...
tape_obj = Tape(tape_path, run_id=rid, resume=True) # 1771  开 tape（append）
bus = EventBus(tape_obj)                            # 1772
try:
    asyncio.run(bus.emit("workflow_cancelled", {"reason": "user_stop"}))  # 1774 ← 无条件
finally:
    ... clear_marker(mpath)                         # 1784
```

`stop` 在 emit 前**没有任何**「tape 是否已终态 / state.status 是否已 cancelled」检查。对照 `run_manager.py:1112` 的 `if handle.status in ("completed","failed","cancelled"): return False` —— **同一项目内已有正确范式**，CLI 路径漏了对齐。

### 2.2 MINOR —— stop 非幂等（违 docstring 自称）

`cli.py:1742` docstring 写「清激活 marker + per-call flock emit `workflow_cancelled`」隐含幂等（「marker 已清就什么都不做」），但实际：tape 几乎不删、不清终态行，重复 `orca stop <rid>` 会**反复 emit** `workflow_cancelled`。无「已 cancelled」短路。tape 因此累积 N 条互斥终态事件。

### 2.3 连带 —— marker 不应作活跃权威

`cli.py:855-863`（`_find_active_run_for_wf` docstring）：

> 「marker 文件存在 ≡ run 活跃（终态时 clear_marker 清掉）…… crash 孤儿 marker 由 doctor 另行检测，§9#2」

`clear_marker` 走 `cli.py:1784` 的 `finally` 链，进程崩溃 / SIGKILL 时不会执行 → marker 残留 → dupe-check 把死 run 当活跃。此契约把 I2 的违反（marker 残留但 run 已终态）的修复甩给**手动** `orca doctor`，在 doctor 跑之前，错误状态对用户可见（stop 选错对象、dupe-check 拒绝新 run）。

### 2.4 终态污染的下游后果

- `events/replay.py:122-138`：reducer 对终态是 **last-writer-wins 覆盖语义**，**不**在第二条终态事件上 raise（见 §6 失败路径）。后果：tape 若含 `workflow_completed` 后再追加 `workflow_cancelled`，replay 静默把 status 从 `completed` 改写成 `cancelled`，**无声**状态污染（completed run 在事后被改判为 cancelled）。
- `iface/web/frontend/src/stores/workflow-store.ts:237`、`iface/web/frontend/src/selectors.ts:264,621,690`：web 状态机按事件序到达消费，第二条终态会触发已完成 run 的状态回跳，UI 与 elapsed/selectors 都假设单终态。
- `iface/cli/widgets/log_stream.py:194`、`iface/mcp/tape_index.py:79`：TUI / MCP 索引按事件渲染，重复终态 = 重复「已取消」横幅 / 重复索引项。

## 3. 不变式 / 契约（铁律，方案不可破）

| ID | 不变式 | 来源 |
|---|---|---|
| **I1** | 一条 tape 至多含一条终态事件（completed/failed/cancelled 互斥） | 单 tape 真相源 + schema 语义 |
| **I2** | run 是否终态的权威判据在 tape（最末终态事件），**不**在 marker | marker.py 模块注释（marker 是 hint，非真相源） |
| **I3** | `orca stop <rid>` 幂等：重复调用追加的事件序列 = 首次（含空集），即终态事件总数随重复调用不增加（首次已 emit 一条 → 后续 emit 空集） | stop docstring 自称 + CLI 幂等约定 |
| **I4** | CLI 路径与 web 路径对同一语义（cancel run）守护同一不变式 I1（DRY：守护逻辑不双写） | phase-3-events §1，CLAUDE.md DRY |
| **I5** | fail loud：未知 / 矛盾状态显式 raise 或显式可观测短路，不静默吞 | CLAUDE.md 铁律 4，replay.py:237 |

## 4. 方案（方向级，不写完整代码）

### 4.1 stop：tape 终态优先，marker 降级为 hint

`stop` 在持 flock 后，emit 前增加一道**只读 fail-loud**终态扫描：

**硬约束 M3（强制）**：终态扫描必须经**纯只读、零副作用**的读路径。**禁止**用 `Tape(tape_path, resume=True).replay()` —— `Tape(resume=True)` 自带「截断残行 / 重写末尾」副作用（又一处静默吞错），与 fail loud 互斥。**禁止**直接复用 `events/tape_reader.py::replay`（**B-2 修正**：实读 `tape_reader.py:47-68` —— `json.JSONDecodeError` 是 **`return` 停整个迭代**，不论中间行还是末尾 partial；`continue` 只在 **pydantic Event 校验失败**路径。该函数 fail-soft：坏 JSON 行下静默停迭代返部分结果 → stop 错走「无终态」分支往坏 tape 追加 `workflow_cancelled`，正是 §6 承诺绝不做的事）。

**新增 fail-loud 终态扫描 reader（B1' / B2' / B-1 / B-2，D1=a）**：

- 走 `tape_reader.replay` 同样的纯只读流式 parse，但**两种失败模式显式分开（B-2）**：
  - `json.JSONDecodeError`（非合法 JSON，含中间残行 / 末尾 partial） → **raise `TapeParseError`**（fail loud 坏数据；历史 tape 损坏不可恢复，必须让人看见）。
  - **pydantic Event 校验失败**（合法 JSON 但不符 schema，如 schema 演化新增 required 字段后读旧 tape） → **`continue` + warn**（**不** raise；schema 演化是可容忍软失败，历史 tape 不应因 schema 升级而阻塞 stop / bootstrap —— 这是「为什么不 raise」的 why）。
- **重复终态检测两套触发显式分开（B-1，方案 b）**：扫过程同时维护
  - `terminal_count: int`（**不去重**，每命中一条终态事件 +1），AND
  - `terminal_types_seen: set[str]`（去重）。
  
  扫完后判定（顺序重要）：
  - `len(terminal_types_seen) > 1`（**不同类型**终态，如 completed+cancelled） → **raise `TapeContradictionError(types=..., last_seq=...)`**（fail loud I5 真损坏；含已见类型集合 + 最末 seq 便于排查）。
  - `terminal_count >= 2` AND `len(terminal_types_seen) == 1`（**同类型重复**，如 2× `workflow_cancelled` —— 正是本 spec 要修的污染历史） → **warn log `[AUDIT] duplicate-terminal types=<...> count=<...>`**，**不阻塞、exit 0、走分支 2 短路**（历史污染非用户当前操作错，不应阻塞其 stop；只 warn 大声报警）。
- 无异常时返 `last_terminal_type | None`（最末命中那条）。
- 不开 `EventBus`、不开写句柄；write 句柄（`Tape(resume=True)` + `EventBus`）只在「真要 emit」分支内才开（控制流骨架见下 B-5）。
- **同一 reader、同一升级行为**被 stop（被操作 tape 异常 → raise / warn）与 `_find_active_run_for_wf`（候选 tape 异常 → 见 §4.2 D2 处理）共享，消灭 B2' 不一致。

**新控制流骨架（B-5，伪代码 —— 防止实现者保留 cli.py:1771-1772 的 bus 外开结构）**：

```
fd = _try_acquire_flock(tape_path)          # 外层
if fd is None: _echo_busy_reply(); return
try:
    reader_result = fail_loud_terminal_scan(tape_path)   # 纯只读，不开 bus
    match branch(reader_result):            # 分支判定见下
        0 (TapeContradictionError):  log [AUDIT]; stderr; raise typer.Exit(1)
        1 (TapeParseError):          stderr; raise typer.Exit(1)
        2 (already-cancelled):       echo {ok,done,note,status}; return
        3 (already-terminal):        echo {ok,done,note,status}; return
        4 (no terminal):
            tape_obj = Tape(tape_path, run_id=rid, resume=True)   # 仅分支4开写句柄
            bus = EventBus(tape_obj)
            try:
                asyncio.run(bus.emit("workflow_cancelled", {"reason":"user_stop"}))
            finally:
                _release_flock(fd); bus.close(); clear_marker(mpath)
                return
finally:                                     # 外层 finally 兜分支 0/1/2/3
    _release_flock(fd); clear_marker(mpath)
```

关键：`Tape(resume=True)` + `EventBus` **只在分支 4 内**实例化；分支 0/1 raise、分支 2/3 return 时**不存在 bus 对象**，bus.close() 调用不存在（防 AttributeError）。

**分支（拿到扫描结果后）**：

0. **reader raise `TapeContradictionError`**（tape 含 ≥2 条**不同类型**终态事件） → **fail loud**：`raise typer.Exit(1)` + stderr + warning log 含 `[AUDIT]` tag（消费路径见 §6 M6'），**不 emit**、**不开写句柄**。
1. **reader raise `TapeParseError`**（坏 tape / 非合法 JSON） → **fail loud**：`raise typer.Exit(1)` + stderr 提示文案见 §6（B6'），**不 emit**、**不开写句柄**。
2. **last_terminal == `workflow_cancelled`**（含 B-1 同类型重复 warn 后的短路） → 短路返 `{ok:true, done:true, note:"already-cancelled", status:"cancelled"}`（满足 I3 幂等）。**不 emit**。
3. **last_terminal ∈ {`completed`,`failed`}** → 短路返 `{ok:false, done:true, note:"already-terminal", status:<那个终态>}`（D4=a：exit 0 + stdout `status` 字段）。**不 emit**、**不改 tape**（满足 I1）。**调用方契约**：必须检 `status` 字段区分 `cancelled`（已被取消过）vs `completed`/`failed`（自然终态）—— exit code 均为 0，区分信息在 `status`。
4. **last_terminal == None** → 开 `Tape(resume=True)` + `EventBus` 写句柄，emit `workflow_cancelled`（按上方骨架的分支 4 控制）。

**marker 清理**：无论上面哪条分支（含 raise 之前的 try/finally）都执行 `clear_marker`（`missing_ok=True`，幂等）。marker 不再作为「run 是否还活跃」的判定输入。

**复用边界（M2 / M5' 澄清）**：本 spec 复用的是 **I1 不变式 + 「最末终态事件扫描」范式**（参考 `_scan_terminal_type`，`run_manager.py:2012-2029`），**机制不共享**：(a) `cancel_run`（`run_manager.py:1094-1113`）守的是 **in-process 内存 `handle.status`**，不靠 tape 扫描；(b) `_scan_terminal_type` 是 **attach 路径**的「跳过终态 follow task」判定（`run_manager.py:2012-2029`），不参与 emit 决策；(c) `stop` 无内存 handle，走 tape 文件扫描。三者守护同一不变式 I1，但机制独立 —— 未来读者勿误判「DRY 未消灭」。helper 抽到 `orca/iface/in_session/` 内（候选：`cli.py` 内私有函数 / 同包新模块），**禁止 import `orca/iface/web/`**（依赖铁律单向：web↔cli 是 iface 兄弟，不互相依赖；公共纯只读 reader 调用 `orca/events/tape_reader` 是合法 events→iface 方向）。

**退出码表（m1）**：

| 分支 | stdout 信封 | exit code |
|---|---|---|
| no-tape | `{ok:true,done:true,note:"no-tape"}` | 0 |
| already-cancelled | `{ok:true,done:true,note:"already-cancelled",status:"cancelled"}` | 0 |
| already-terminal | `{ok:false,done:true,note:"already-terminal",status:<completed\|failed>}` | 0（业务可恢复，对齐 web `cancel_run` 返 False） |
| emit 成功 | `{ok:true,done:true}` | 0 |
| 坏 tape（`TapeParseError`） | stderr（文案见 §6 B6'） | 1（`raise typer.Exit(1)`） |
| **矛盾终态（`TapeContradictionError`，不同类型）** | stderr + `[AUDIT]` warning log | 1（`raise typer.Exit(1)`） |
| **同类型重复终态（B-1，2× workflow_cancelled）** | `{ok:true,done:true,note:"already-cancelled",status:"cancelled"}` + warn log `[AUDIT] duplicate-terminal` | 0（不阻塞，warn 大声报警） |
| flock busy | `{done:false,reason:"busy",retry_after_ms:500}` | 0（沿用现行） |

**F3 封口**：`status` 字段**仅在** `already-cancelled` / `already-terminal` 分支出现；其他分支（no-tape / emit 成功 / busy / raise）调用方**不得依赖其存在**。

### 4.2 `_find_active_run_for_wf`：tape 派生活跃性，marker 仅作候选索引

把「marker 存在 ≡ 活跃」改为「marker 存在 → 候选；tape 是否已终态才是活跃判据」：

1. 遍历 marker 文件得到候选 markers（不变，O(N) 扫）。
   - **B-3 flood 计数**：若 `len(候选 markers) > 5` → warn log `[AUDIT] candidate-marker-flood count=<N>`，**不阻塞**，继续 step 2。
2. **B-4 wf_name 过滤**：对每个候选 marker，按其 run_id 读 tape 头部 `workflow_started.workflow_name`（保留现行 `_read_workflow_name` head-scan，`cli.py:855-874`），与目标 `wf_name` 不等 → 跳过该候选（不进 step 3）。**先 wf_name 过滤，再终态扫描**：否则候选 marker 属 wf X + tape 无终态会被误判为「wf Y 的活跃 run」，错误拒绝用户 bootstrap wf Y。
3. 对**匹配候选**（wf_name 相等）按 run_id 读 tape 的最末终态事件（用 §4.1 的 fail-loud reader）。**候选异常处理（D2=a，B3'，B-6 per-candidate 骨架）**：
   - 候选 tape 不存在 → 跳过该候选（对齐 `cli.py:846-847` 现状「tape 读失败 → 跳过（不误判）」）。
   - 候选 tape 非合法 JSON（reader raise `TapeParseError`） → **warn log `[AUDIT] candidate-tape-corrupted run=<rid>` + 跳过该候选**（保守判该 run 不活跃）。
   - 候选 tape 含矛盾终态（reader raise `TapeContradictionError`，I1 已破） → **warn log `[AUDIT] candidate-tape-contradiction run=<rid>` + 跳过该候选**（G2：与 parse 失败分级，符合 I5 可观测分级）。
   - 候选 tape 含同类型重复终态（reader warn `[AUDIT] duplicate-terminal`） → 视为已终态，跳过该候选（不返回）。
   - 无终态事件 → 真·活跃（返回该 run_id）。
   - 有终态事件 → 死 run 残留 marker，**跳过**（不返回）。
4. 此变化**消除** §2.3 的「crash 到手动 doctor 之间死 run 被当活跃」窗口 —— 不依赖 doctor 即可自愈。
5. docstring 同步改写：删「marker 文件存在 ≡ run 活跃」，改为「tape 终态判活跃，marker 仅索引候选」。

**per-candidate 隔离骨架（B-6，防止实现者把 try 包在整个 marker 循环外 → 单候选损坏阻塞全部 bootstrap）**：

```
candidate_markers = sorted(rundir.glob("orca-*.json"))     # step 1
if len(candidate_markers) > 5:
    warn [AUDIT] candidate-marker-flood count=...
for mp in candidate_markers:                               # step 2/3 — per-candidate
    marker = read_marker(mp)
    if marker is None: continue
    tape_path = rundir / f"{marker.run_id}.jsonl"
    if _read_workflow_name(tape_path) != wf_name: continue # step 2 wf_name 过滤
    try:                                                    # 单候选作用域，禁包在循环外
        term = fail_loud_terminal_scan(tape_path)
    except TapeParseError:
        warn [AUDIT] candidate-tape-corrupted run=...; continue
    except TapeContradictionError:
        warn [AUDIT] candidate-tape-contradiction run=...; continue
    if term is None:
        return marker.run_id                               # 真·活跃
    # else 已终态 → 跳过（含 duplicate-terminal 的 warn 已在 reader 内打出）
return None
```

**`_find_active_run_for_wf` 不 raise**：活动性查询的本职是「找有没有活跃 run」，不是「报 tape 错」，让无关 run 的坏 tape 阻塞所有 bootstrap 是回归。**raise 仅留给 `stop`**（被操作 tape 才 raise，§4.1 分支 0/1）。

**唯一调用点（M4）**：grep 证实 `_find_active_run_for_wf` 仅被 `cli.py:1097`（`bootstrap` dupe-check）调用。须文档化的 **UX 变化**：

| 场景 | 现行行为 | 改后行为 |
|---|---|---|
| 死 marker 残留（marker 在 + tape 已终态）+ 用户 bootstrap 同 wf | **拒绝**建新 run（报「已有活跃 run」） | **静默建新 run**（死 marker 不再阻塞） |
| 其他 run 坏 tape（候选损坏 / 矛盾）+ 用户 bootstrap 同 wf | silent skip（cli.py:859-860） | **warn `[AUDIT] candidate-tape-{corrupted,contradiction}` 跳过该候选**（多一行 warn，不阻塞 bootstrap） |

死 marker 行是 UX 改善（用户不再被 crash 孤儿 marker 卡住）；候选坏 tape 行仅多一行 warn，不阻塞。均属可见行为变化，须 release note 标注。

### 4.3 doctor 角色收敛（顺带澄清，非主线）

孤儿 marker（marker 存在 + tape 已终态）经 4.2 后已**不再制造误判**。`doctor` 的 `marker_orphan` 检查保留作清理工具（主动清死 marker 释放目录条目），但**不再是正确性的依赖** —— 即 doctor 不跑，系统也自洽。spec 不动 doctor 实现。

## 5. 范围边界

### 5.1 In-scope

- `orca/iface/in_session/cli.py::stop`：增加 emit 前 fail-loud 终态扫描 + 四分支短路（§4.1）+ 退出码表。
- `orca/iface/in_session/cli.py::_find_active_run_for_wf`：改活跃判据为 tape 终态派生；docstring 改写。
- **新增 fail-loud 终态扫描 reader**（B1）：纯只读、零副作用、对残行/parse 失败 raise。落点：`orca/iface/in_session/` 内（cli.py 私有函数 / 同包新模块）。**禁止 import `orca/iface/web/`**（依赖铁律）；调用 `orca/events/tape_reader` 是合法 events→iface 单向依赖。
- stop 的 `note` 字段语义扩展（`already-cancelled` / `already-terminal` / 既有 `no-tape`）+ 退出码表，文档化在 docstring。
- 测试：见 §7。

### 5.2 Out-of-scope（显式排除）

- **`cc_nudge.sh::_scan_my_active_run_ids`（B2 修订）**：实读 `orca/iface/in_session/templates/cc_nudge.sh:137-158` —— glob `runs/orca-*.json` 取 marker 存在即活跃，**与 `_find_active_run_for_wf` 同一个「marker≡活跃」坏判据**。本 spec 修 `_find_active_run_for_wf` 后，cc_nudge 仍按 marker 残留给主 session 注入「你有活跃 run」提醒文本。**已知欠债，显式接受其滞后**：cc_nudge 仅 UX 提醒（不锁 session、不阻塞 workflow 操作、不写 tape），错判后果是「多一句提醒文本」，可接受；正确修法是 cc_nudge 内嵌 tape 终态检查（bash + jq），单独立项另案。**本 spec 不留「非 bug」字样**。
- **`events/replay.py` 增加「多终态事件 raise」校验**：理论上更 fail loud，但：(a) tape 已经是 append-only 历史事实，replay 时 raise 等于让所有读路径崩溃，反而扩大爆炸半径；(b) 正确做法是**在写入侧**（emit 侧）守护 I1，本 spec 在 stop 写入侧堵漏即足够。replay 端的鲁棒性（如何对待历史坏 tape）单独立项。
- **marker 字段调整 / ActivationMarker schema 变更**：marker 保持 3 字段。本 spec 不动 marker.py 数据形状。
- **stop 的 flock 语义变更**：per-call flock 行为不变（仍 LOCK_EX | LOCK_NB，busy → 0 退出 `_echo_busy_reply`）。
- **tape 截断 / 删除**：本 spec 不删 tape 行、不截断。stop 幂等通过「不再追加」实现，不通过「删除已追加」实现（append-only 铁律）。
- **`workflow_cancelled` 之外的终态 emit 路径审计（M1）**：orchestrator 的 `make_workflow_failed` / `make_workflow_completed`（`orchestrator.py` 多处 emit）同样不扫 tape 终态，靠「单 task + flock」隐式保证 I1，**未审计**。本 spec 仅覆盖 stop 路径；I1 在 orchestrator 路径的全局守护列后续 audit spec（标记为已知未覆盖）。

## 6. 失败路径（如何 fail loud）

| 场景 | 行为 | 可观测 |
|---|---|---|
| tape 不存在 | 维持现行：仅清 marker，返 `{ok:true,done:true,note:"no-tape"}`，exit 0 | `cli.py:1760-1764` 已有 |
| tape 损坏 / 半写（reader raise `TapeParseError`） | **fail loud**：catch → `raise typer.Exit(1)` + stderr「tape 损坏:<path>,请手动核查（doctor 暂不修复 tape 内容）」（B6'），**不 emit**、**不开写句柄**、**不**回退到「无终态 → 直接 emit」 | **绝对禁止**用 `events/tape_reader.replay`（B1：它对中间残行 `continue`、末尾 partial 静默 return，会返空让 stop 错走 emit 分支）；必须用 §4.1 的 fail-loud reader。**doctor 当前 6 个 check 无 tape-corruption 修复路径**（`cli.py:2067-2199` 实读：skill_install / cli_imports_ok / diag_switch / advance_hook / sidechain_backend / sidechain_daemon_liveness），故 stderr 文案不承诺 doctor 修复，仅提示手动核查；扩 doctor 实现不在本 spec |
| flock 撞锁（另一 CLI 持锁） | 维持现行：`_echo_busy_reply()` + 0 退出 | `cli.py:1767-1769` 已有 |
| 终态扫描发现矛盾（reader raise `TapeContradictionError`，tape 已含 ≥2 条**不同类型**终态事件） | **fail loud**（I5 真损坏）：`raise typer.Exit(1)` + stderr + warning log 含 `[AUDIT]` tag；**不**追加第三条；**不**静默 short-circuit | I1 已被旧污染破坏时，本 spec **不扩大**污染且**大声报警**；历史坏 tape 的修复单独立项 |
| **同类型重复终态（B-1，2× workflow_cancelled）** | warn log `[AUDIT] duplicate-terminal types=<...> count=<N>` + 走分支 2 短路；**exit 0、不阻塞、不追加** | 历史污染非用户当前操作错，**不应阻塞其 stop**；同类型重复不构成「矛盾状态」（状态字段语义唯一），但需大声报警供未来治理 |
| tape 存在但 0 事件（G5） | reader 返 `None` → 走分支 4 emit `workflow_cancelled` | `apply_event` reducer 不检查 `workflow_started` 存在性（`replay.py:134-138`），emit 后 replay 仍合法产出 `status="cancelled"`。此行为**显式接受**（空 tape + stop 等价于「取消一个未启动的 run」），但须显式登记，不容隐式 |
| `clear_marker` 失败 | 维持现行：warn 不 raise（`marker.py:108-110`） | marker 残留非致命（4.2 后不再制造误判） |

**`[AUDIT]` tag 消费路径声明（M6'）**：实读全仓库，无 `[AUDIT]` 历史先例与现存消费者。本 spec 不引入新消费者 —— **stderr 是当前唯一消费路径**（人类可读）；`[AUDIT]` tag 作为**机器可 grep 锚点**保留，供未来 (a) doctor 接入 tape-corruption 检查时 grep 此 tag、或 (b) 监控 / log 系统接入。当前不消费 ≠ 无价值，但本 spec 不为之引入新代码。

## 7. 测试意图（覆盖意图，非行为枚举）

依 CLAUDE.md 规则 9「Tests verify intent, not just behavior」，每条测**不变式**而非**实现**：

1. **I1 / 已终态 run 调 stop 不追加事件**：构造 tape 已含 `workflow_completed`（或 `workflow_failed`）+ marker 残留 → 调 `orca stop <rid>` → 断言：tape 行数不变、无新 `workflow_cancelled`、退出信封 `note=="already-terminal"` 且 **`status` 字段 == tape 最末终态类型**（D4=a，调用方据 `status` 区分 `cancelled` vs `completed`/`failed`）。
2. **I3 / 重复 stop 幂等**：tape 已含 `workflow_cancelled` → 连调两次 `orca stop <rid>` → 断言：tape 行数始终不变、两次都返 `already-cancelled`、marker 被清（幂等）。
3. **I3 / 活跃 run 调 stop 仍 emit 一条**：tape 仅含 `workflow_started` + `node_*`，无终态 → 调 `orca stop <rid>` → 断言：tape 追加**恰好一条** `workflow_cancelled`、marker 清除。
4. **I2 / `_find_active_run_for_wf` 不把死 run 当活跃**：rundir 含一个 marker，其 tape 已含终态事件 → 调用返 None（不返回该 run_id）。
5. **I2 / `_find_active_run_for_wf` 真活跃仍命中**：rundir 含 marker，其 tape 无终态事件 → 调用返该 run_id。
6. **I5 / tape 半写时 stop fail loud**：构造坏 tape（截断 JSON 行）+ marker 残留 → 调 `orca stop <rid>` → 断言：**exit code = 1**、stderr 含「doctor」、错误信息可观测、**不**追加 `workflow_cancelled`。
7. **回归 / no-tape 路径不变**：tape 不存在、marker 残留 → 调 `orca stop <rid>` → 断言：返 `no-tape`、marker 被清、不 raise。
8. **I2 / bootstrap 端到端（M4）**：rundir 含一个死 marker（marker 在 + tape 已终态）+ 用户调 `orca bootstrap` 同 wf → 断言：成功建新 run（不再被死 marker 拒绝），与现行「拒绝建新 run」行为变化对齐 §4.2 UX 表。
9. **I5 / 终态扫描发现矛盾终态（m5）**：构造坏 tape 含 `workflow_completed` + `workflow_cancelled` 两条 → 调 `orca stop <rid>` → 断言：**exit code = 1**、stderr/log 含 `[AUDIT]` tag、**不**追加第三条终态事件。
10. **m6 / 候选 marker 堆积告警**：rundir 含 6 个孤儿 marker（各自 tape 已终态）→ 调 `orca stop <rid>` 或 `orca bootstrap` 同 wf → 断言：warn log 含 `[AUDIT] candidate-marker-flood`、不阻塞操作（stop 走分支、bootstrap 建新 run 成功）。
11. **F5 / 候选坏 tape 不阻塞 bootstrap（D2=a 端到端）**：rundir 含 N 个候选 marker，其中 1 个对应 tape 损坏（中间行非合法 JSON），其余 tape 已终态 / 属其他 wf → 调 `orca bootstrap` 同 wf → 断言：warn log 含 `[AUDIT] candidate-tape-corrupted run=<那 rid>`、bootstrap **成功建新 run**、**不 raise**。
12. **F6 / 同类型重复终态不阻塞 stop（B-1）**：tape 含 2× `workflow_cancelled`（历史污染）+ marker 残留 → 调 `orca stop <rid>` → 断言：warn log 含 `[AUDIT] duplicate-terminal`、**exit 0**、tape 行数不变（**不**追加第三条）、退出信封 `note=="already-cancelled"`。

## 9. 依赖与风险

- **依赖铁律**：终态扫描 helper 必须放在 iface 层共享位置，不反向调 web。`tape_reader` 已在 events 层（合法方向）。
- **风险 R1**：扫描 tape 增加单次 stop / dupe-check 的读开销。缓解：tape 单遍扫，活跃 run 通常 tape 行数有限；候选 marker 数通常 ≤1。**候选 marker > 5 时 warn log `[AUDIT] candidate-marker-flood`**（m6：>5 几乎必然是孤儿 marker 堆积，stop/dupe-check 扫描开销线性增长；不阻塞操作，AC见 A11）。
- **风险 R2（B3 / m7 修订）**：**原「所有写路径持同一 flock」表述事实错误，已撤回。** grep `run_manager.py` 全文无 flock；web `cancel_run`（`run_manager.py:1094-1149`）走 in-process EventBus，**不持 OS flock**。CLI stop 持的 flock 与 web 的 in-process emit **互不可见**，二者并发仍能各 emit 一条 `workflow_cancelled`，破 I1。
  - 本 spec 缓解仅覆盖 **CLI↔CLI 跨进程并发**（POSIX flock 临界区内完成扫描+决策+emit）。
  - **已知欠债，显式承认未覆盖**：(a) web `cancel_run` 与 CLI stop 跨边界并发；(b) **G4：orchestrator in-process emit（`make_workflow_failed` / `make_workflow_completed`）与 CLI stop 同样存在跨进程 race** —— orchestrator 在 web 进程内直接 `bus.emit`，CLI stop 持 flock 不互见，结构与 web `cancel_run` race 同构；同属本 spec 未覆盖欠债。强制 `cancel_run` / orchestrator acquire 同一把 flock 涉及跨进程锁协议设计（flock 文件路径、释放时机、与 in-process asyncio task 协调），**超出本 spec**，列后续 spec。
  - **Windows**：in_session CLI 全模块 **POSIX-only 由 ADR I3.3 锚定**（`cli.py:29` 顶层 `import fcntl`，无 fallback），本 spec **继承该前提**，不重新推导 Windows flock 行为；POSIX-only 范围与 ADR I3.3 一致，超出本 spec。
- **风险 R3**：用户期望「stop 已 completed 的 run」报错。本 spec **定调**：选**短路 + 可观测 note + exit 0**（业务可恢复语义，对齐 web `cancel_run` 返 False）。`already-terminal` 分支不 raise。调用方靠 stdout `status` 字段区分自然终态（D4=a），不靠 exit code。
